# 三个创新点：机制、证据、答辩口径

> 定位原则：创新点必须落在**机制**上，不能落在技术选型上。使用大模型、RAG、知识图谱、Nexent、MCP、多 Skill、可视化页面，全部只是实现条件，不构成创新。以下三点才是 PPT、Demo 与答辩需要逐条证明的对象。

## 创新点一：事件驱动的城市语义层自动演化

### 机制

不是"先建好一张静态图谱再问答"，而是**新数据进场即触发知识变更提案**：

```
新资产（公告/气象/工单/施工计划）
   → 抽取候选三元组（复用 ontology_bootstrap）
   → 差异比对：新增 / 冲突 / 失效
   → EvolutionProposal（含影响评估）
   → 人工确认（accept / reject / merge）
   → 版本发布（kb-vX.Y.Z + snapshot_hash）
   → 一键回滚（指针回退，历史保留）
```

关键区别于普通知识图谱：**提案自带影响评估**（受影响的实体、规则、历史结论数量），人工确认前就知道"改这一条会动到什么"。

### 数据模型

```python
class EvolutionProposal(StrictModel):
    proposal_id: str
    trigger_asset_ids: list[str]        # 触发本次演化的资产
    base_version: str                   # kb-v1.2.0
    added_triples: list[SemanticTriple]
    removed_triple_ids: list[str]
    conflicted_triple_ids: list[str]    # 与新证据矛盾的在库三元组
    affected_twin_ids: list[str]        # 图邻接 2 跳内受影响实体
    affected_rule_ids: list[str]
    stale_claim_count: int              # 引用将失效证据的历史断言数
    risk_flags: list[str]               # 覆盖职责关系/删除证据等高风险变更
```

### 可演示动作（评委可现场触发）

1. 放入一份"施工延期公告"，系统 30 秒内产出提案：新增 `CP-2026-041` 有效期延长三元组，标记 1 条受影响历史结论。
2. 拒绝其中一条候选 → 版本不发布，审计记录留存。
3. 接受 → 发布 `kb-v1.3.0`，影响评估显示"2 条历史推演需重新评估"。
4. 一键回滚到 `kb-v1.2.0`，再次查询得到回滚前结果（可复现）。

### 量化证据

- 提案精确率 = 被人工接受的候选数 / 提案总数（合成数据集目标 ≥ 80%）。
- 影响评估召回率 = 系统标记受影响实体 ∩ 人工标注 / 人工标注（目标 100%，宁可多报不可漏报）。
- 回滚可复现性：回滚后 `snapshot_hash` 与发布前一致（硬性断言）。

### 落在哪

`P3` 扩展 `ontology.py` 版本发布为提案-确认-发布-回滚闭环；`P4` 提供图邻接扩散与历史 claim 反查。

## 创新点二：面向跨部门协同的因果推演与反事实

### 机制

输出不是"哪些道路受影响"的列表，而是一条**可解释因果链**，每个节点是一条带证据的断言，边是规则：

```
暴雨增强(WA-01) → 排水能力不足(PL-DRN-101 DN600 + DF-PS-01 故障)
→ R-101 积水(WO-007, 30cm) → 燃气基坑施工受阻(CP-041)
→ 燃气/交通同时响应 → 封路与抢修资源冲突(C1/C3)
→ 调整处置顺序（先隔离风险源，后抽排）
```

因果链实现为 **DAG 上的前向链**，不是模型自由叙述。每个节点存 `premise_step_ids`，因此每条边都能被追问"凭什么"。

### 反事实 = 对同一 DAG 做节点干预后重放

```python
def counterfactual(
    dag: DeductionGraph,
    intervention: dict[str, str],   # step_id -> 强制取值
    question: str,
) -> CounterfactualResult:          # diff: 新增/消失节点、缺口变化、风险等级变化
```

三个必答反事实：

| 问题 | 干预方式 | 期望输出 |
| --- | --- | --- |
| 先封路再隔离风险源会怎样 | 交换 stage 5/6 顺序 | 抢修车辆可达性下降，燃气到场时间后移，受影响抢修路径集合（实测：J-01↔J-02 由 820 m/1.2 分钟变为 3860 m/6.3 分钟，绕行经 R-102/R-103/R-104） |
| 抽水泵不足时优先保障谁 | `RES-PUMP-M.qty=2` | 缺口按片区给出，保居民区 vs 保基坑的优先级有依据（实测：A-03 需 5 台/本区 2 台/缺 3，B-01 需 2 台/本区 0 台/缺 2，优先 A-03） |
| 施工延期一天风险是否扩大 | `CP-2026-041.end_at += 1d` | 开挖面暴露跨越降雨窗口，二次风险上调（实测：orange 6h → red 12h，风险升档） |

**反事实必须由同一套规则与语义层重放得出**，不能由大模型另写一段解释——否则与"可验证"自相矛盾。

### 量化证据

- 因果链节点证据覆盖率 100%（无证据节点直接不输出）。
- 反事实一致性：干预节点在结果中保持不变（硬性断言）。
- 路径正确率 ≥ 80%（对照 `docs/urban-scenario-ground-truth.md` 六跳）。

### 落在哪

`P6` 推演链；`deduction.py` 的 `DeductionGraph` 需支持 `intervene()` 与 `diff()`。

## 创新点三：推理结果的可验证数据血缘与影响分析

### 机制

多数项目只追踪"答案引用了哪份文档"。本项目追踪**变更传播链**：

```
数据变更（资产改版/废弃）
  → 知识变更（三元组新增/失效）
  → 推理变更（哪些 claim 失效）
  → 建议变更（哪些处置建议需重新评估）
```

实现靠三层反向索引 + 最小重算：

```
asset_id ──▶ triple_id ──▶ claim_id ──▶ decision_id / skill_result_id
```

```python
class ImpactReport(StrictModel):
    change_id: str                  # 哪次变更
    changed_assets: list[str]
    stale_triples: list[str]
    stale_claims: list[str]
    stale_decisions: list[str]
    needs_recompute: bool
    minimal_recompute_set: list[str]   # 最小需重算的 claim 集合
    reason: str
```

关键差异：**不是全量重跑**，而是算出最小受影响子图。这既省算力，也让"影响范围"本身成为可展示的结论。

### 可演示动作

1. 把 `notice_gas_construction.md` 升到 v2（施工延至次日）→ 系统提示"3 条历史推演、1 条处置建议需重新评估"，并列出是哪 3 条。
2. 人工修正一条管线关系（`PL-GAS-101` 埋深 2.5m → 3.2m）→ 提示原"悬空风险"判定依据已变。
3. 把 v2 预案置为过期 → 所有引用其阈值的结论标记失效，且**不得**自动改用 v1。

### 量化证据

- 漏报率 0：应失效结论必须全部被标记（对照人工标注集）。
- 重算范围比 = 需重算 claim 数 / 全量 claim 数（目标 < 30%，体现"最小"）。
- 血缘完整性：任一结论可回指到 `asset_id#locator` + 版本 + 快照哈希（硬性门禁）。

### 落在哪

`P4` 的 `provenance.py`（哈希链 + `trace_claim`）+ `P8` 的影响分析评测。

## 宣传语（统一口径）

> 提出一种面向城市基础设施突发事件的可演化语义数字孪生方法：通过多模态数据资产认知自动更新城市事件知识图谱，利用 Nexent MCP + Skills 编排跨部门因果推演，并沿数据血缘追踪推理结果和处置建议的影响范围。

## 30 秒答辩口径

1. 知识不是建完就静态：新公告进来，系统自己提出该改哪条关系、影响哪些历史结论，人确认后才发布，能回滚。
2. 推演不是列受影响清单：给的是暴雨→能力不足→积水→施工受阻→部门冲突→调整顺序的因果链，并且能回答"如果先封路会怎样"这种反事实。
3. 结论不是只有引用：数据一改，系统能说出哪几条历史结论、哪几条处置建议已经不可信，且只重算这一小部分。
