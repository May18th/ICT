# 四个创新点：机制、证据、答辩口径

> 定位原则：创新点必须落在**机制**上，不能落在技术选型上。使用大模型、RAG、知识图谱、Nexent、MCP、多 Skill、可视化页面，全部只是实现条件，不构成创新。以下三点才是 PPT、Demo 与答辩需要逐条证明的对象。

## 创新点一：事件驱动的城市语义层自动演化

### 机制

不是"先建好一张静态图谱再问答"，而是**新数据进场即触发知识变更提案**：

```
新资产（公告/气象/工单/施工计划）
   → 抽取候选三元组（复用 ontology_bootstrap）
   → 差异比对：新增 / 冲突 / 失效
   → EvolutionProposal（含影响评估）
   → 人工确认（accept / reject / merge）
   → 版本发布（kb-vX.Y.Z + snapshot_hash）
   → 一键回滚（指针回退，历史保留）
```

关键区别于普通知识图谱：**提案自带影响评估**（受影响的实体、规则、历史结论数量），人工确认前就知道"改这一条会动到什么"。

### 数据模型

```python
class EvolutionProposal(StrictModel):
    proposal_id: str
    trigger_asset_ids: list[str]        # 触发本次演化的资产
    base_version: str                   # kb-v1.2.0
    added_triples: list[SemanticTriple]
    removed_triple_ids: list[str]
    conflicted_triple_ids: list[str]    # 与新证据矛盾的在库三元组
    affected_twin_ids: list[str]        # 图邻接 2 跳内受影响实体
    affected_rule_ids: list[str]
    stale_claim_count: int              # 引用将失效证据的历史断言数
    risk_flags: list[str]               # 覆盖职责关系/删除证据等高风险变更
```

### 可演示动作（评委可现场触发）

1. 放入一份"施工延期公告"，系统 30 秒内产出提案：新增 `CP-2026-041` 有效期延长三元组，标记 1 条受影响历史结论。
2. 拒绝其中一条候选 → 版本不发布，审计记录留存。
3. 接受 → 发布 `kb-v1.3.0`，影响评估显示"2 条历史推演需重新评估"。
4. 一键回滚到 `kb-v1.2.0`，再次查询得到回滚前结果（可复现）。

### 量化证据

- 提案精确率 = 被人工接受的候选数 / 提案总数（合成数据集目标 ≥ 80%）。
- 影响评估召回率 = 系统标记受影响实体 ∩ 人工标注 / 人工标注（目标 100%，宁可多报不可漏报）。
- 回滚可复现性：回滚后 `snapshot_hash` 与发布前一致（硬性断言）。

### 落在哪

`P3` 扩展 `ontology.py` 版本发布为提案-确认-发布-回滚闭环；`P4` 提供图邻接扩散与历史 claim 反查。

## 创新点二：面向跨部门协同的因果推演与反事实

### 机制

输出不是"哪些道路受影响"的列表，而是一条**可解释因果链**，每个节点是一条带证据的断言，边是规则：

```
暴雨增强(WA-01) → 排水能力不足(PL-DRN-101 DN600 + DF-PS-01 故障)
→ R-101 积水(WO-007, 30cm) → 燃气基坑施工受阻(CP-041)
→ 燃气/交通同时响应 → 封路与抢修资源冲突(C1/C3)
→ 调整处置顺序（先隔离风险源，后抽排）
```

因果链实现为 **DAG 上的前向链**，不是模型自由叙述。每个节点存 `premise_step_ids`，因此每条边都能被追问"凭什么"。

### 反事实 = 对同一 DAG 做节点干预后重放

```python
def counterfactual(
    dag: DeductionGraph,
    intervention: dict[str, str],   # step_id -> 强制取值
    question: str,
) -> CounterfactualResult:          # diff: 新增/消失节点、缺口变化、风险等级变化
```

三个必答反事实：

| 问题 | 干预方式 | 期望输出 |
| --- | --- | --- |
| 先封路再隔离风险源会怎样 | 交换 stage 5/6 顺序 | 抢修车辆可达性下降，燃气到场时间后移，受影响抢修路径集合（实测：J-01↔J-02 由 820 m/1.2 分钟变为 3860 m/6.3 分钟，绕行经 R-102/R-103/R-104） |
| 抽水泵不足时优先保障谁 | `RES-PUMP-M.qty=2` | 缺口按片区给出，保居民区 vs 保基坑的优先级有依据（实测：A-03 需 5 台/本区 2 台/缺 3，B-01 需 2 台/本区 0 台/缺 2，优先 A-03） |
| 施工延期一天风险是否扩大 | `CP-2026-041.end_at += 1d` | 开挖面暴露跨越降雨窗口，二次风险上调（实测：orange 6h → red 12h，风险升档） |

**反事实必须由同一套规则与语义层重放得出**，不能由大模型另写一段解释——否则与"可验证"自相矛盾。

### 量化证据

- 因果链节点证据覆盖率 100%（无证据节点直接不输出）。
- 反事实一致性：干预节点在结果中保持不变（硬性断言）。
- 路径正确率 ≥ 80%（对照 `docs/urban-scenario-ground-truth.md` 六跳）。

### 落在哪

`P6` 推演链；`deduction.py` 的 `DeductionGraph` 需支持 `intervene()` 与 `diff()`。

## 创新点三：推理结果的可验证数据血缘与影响分析

### 机制

多数项目只追踪"答案引用了哪份文档"。本项目追踪**变更传播链**：

```
数据变更（资产改版/废弃）
  → 知识变更（三元组新增/失效）
  → 推理变更（哪些 claim 失效）
  → 建议变更（哪些处置建议需重新评估）
```

实现靠三层反向索引 + 最小重算：

```
asset_id ──▶ triple_id ──▶ claim_id ──▶ decision_id / skill_result_id
```

```python
class ImpactReport(StrictModel):
    change_id: str                  # 哪次变更
    changed_assets: list[str]
    stale_triples: list[str]
    stale_claims: list[str]
    stale_decisions: list[str]
    needs_recompute: bool
    minimal_recompute_set: list[str]   # 最小需重算的 claim 集合
    reason: str
```

关键差异：**不是全量重跑**，而是算出最小受影响子图。这既省算力，也让"影响范围"本身成为可展示的结论。

### 可演示动作

1. 把 `notice_gas_construction.md` 升到 v2（施工延至次日）→ 系统提示"3 条历史推演、1 条处置建议需重新评估"，并列出是哪 3 条。
2. 人工修正一条管线关系（`PL-GAS-101` 埋深 2.5m → 3.2m）→ 提示原"悬空风险"判定依据已变。
3. 把 v2 预案置为过期 → 所有引用其阈值的结论标记失效，且**不得**自动改用 v1。

### 量化证据

- 漏报率 0：应失效结论必须全部被标记（对照人工标注集）。
- 重算范围比 = 需重算 claim 数 / 全量 claim 数（目标 < 30%，体现"最小"）。
- 血缘完整性：任一结论可回指到 `asset_id#locator` + 版本 + 快照哈希（硬性门禁）。

### 落在哪

`P4` 的 `provenance.py`（哈希链 + `trace_claim`）+ `P8` 的影响分析评测。

## 创新点四：稀缺资源的决策策略受控进化

### 机制

前三个创新点解决"看得懂、推得演、信得过"，但赛题 3 追问的是**智能体自己从反馈里变更好了没有**：
"从哪一次推演的结果、基于什么信号、调整了什么策略，从而让下一次更优？"

P9 把这条链做成可运行闭环，选"跨片区抽排资源分配"作为决策对象（六跳只回答缺多少台，不回答先给谁）：

```
推演输出 decision_inputs（每片区：深度/封路判定/危险源/需求/本区库存）
  → AllocationPolicy.decide()（策略版本 vN）
  → AllocationDecision{分配、跨区调拨、未满足、优先序}
  → 与冻结 ground truth 比 → DeviationReport{4 维偏差 + 归因}
  → 按最差维度生成候选 → 训练集选优 → 评测门禁（留出集不退化 + 不违反评审）→ promote / reject
  → 版本标签 flood-response-v1.N + 版本历史留痕 + 一键回滚 + 反馈指纹校验
```

P9.1 再把它从"一次演示"变成"持续机制"，三个机制直击评委追问：

1. **分层决策记忆（跨会话沉淀）**：每次进化把"场景签名 → 已验证有效的策略 → 实际偏差"写进
   Tenant/User/Agent 三层经验库，下次同类场景从记忆 warm start，而不是从 v1 重搜。
2. **人工评审第二反馈通道**：领域负责人（演示中角色扮演）对方案做修正，修正转成**自包含评审用例**
   进入门禁——候选不满足评审结论即被拒，"避免同类否决"因此可断言。
3. **语义化策略版本**：每次采纳产出 `flood-response-v1.N`，记录触发反馈 ID、触发评审 ID、参数变更、
   预期改善；被拒候选只留痕不发标签。

两个关键区别：

1. **进化的是策略，不是结论**：推演结论是输入，参数化的是"先保谁、能不能跨区调"。
   不会出现"为了指标好看去改推演结果"。
2. **拒绝也是证据**：门禁拒绝时 active 版本不变；收敛后主动探一次更激进的候选被拒——
   证明"多调拨不是更好"，而不是跑到 0 就停。

### 可演示动作（评委可现场触发）

1. 跑 `python -m decision_poc.policy_evolution` → 第一次会话 3 轮：第 1 轮学到"已过封路阈值优先"
   （`flood-response-v1.1`），第 2 轮补"次生危险源也算关键"（`v1.2`），第 3 轮激进探针被门禁拒绝。
2. 同一次演示里第二次会话从**分层记忆** warm start：起点偏差 `0.0000`（第一次是 `0.2264`），
   只需 1 轮收敛探针——经验沉淀直接可见。
3. 人工评审 `REV-001` 提出的修正（从 B-01 调 1 台给 A-03）：评审用例偏差 `0.1171 → 0.0000`，
   后续候选违反该结论会被门禁拒绝。
4. 真实事件 `WO-20261029-007`：进化前 `A-03 4 台 / B-01 2 台`，A-03 缺 1 台；
   进化后 `A-03 6 台 / B-01 0 台`，A-03 补齐，B-01 缺口显式上报，跨区时延 40 分钟来自台账。
5. 回滚到 v1：训练偏差逐位回到 `0.2264`，再恢复最终版本。
6. Nexent 侧通过 MCP 工具 `allocation_plan` 调用同一个策略（`policy` 参数可传进化后的版本）。
7. 浏览器面板 `http://127.0.0.1:8787/evolution`（`web_demo` 启动后）把上述 1–6 条同屏展示：
   指标卡、进化前后表、记忆命中、评审修正、版本标签、真实事件分配对比；页脚固定印三条表述边界，
   评委可自己点开核对，不依赖讲者口述。
8. Nexent 真机：平台对话选 `urban_deduction_agent` 问 `WO-20261029-007`，回答为六跳 JSON；
   再跑 `python -m decision_poc.nexent_urban` 输出 **8/8 一致**（conversation_id=78）；
   指出 `samples/nexent/live/mcp_tool_log.jsonl` 中 `event_deduce` 与它的协议修复重试
   是平台调用的——证明结论不是本地脚本自演。

- 反馈指纹 sha256 可复算，反馈被改动即失配。

### 落点

`deduction.py` 的 `decision_inputs`（推演只给事实，不下决策）+ `allocation.py`（策略/分配/偏差）+
`policy_evolution.py`（归因/候选/门禁/版本标签/回滚）+ `experience.py`（分层记忆/人工评审）+
`mcp_server.py` 的 `allocation_plan`。

### 表述红线

口径统一为**受控评测环境下的反馈信号**（冻结 ground truth + 人工评审），不宣称真实市政数据回流、不宣称在线学习；
进化能力由"偏差归因 + 受控候选 + 门禁 + 版本标签 + 回滚"体现，不包装成模型自训练。
两条硬边界必须写明：

- 分层记忆是**离线同构契约**（Tenant/User/Agent 与 Nexent 分层记忆对齐），**未在真实 Nexent 平台真机验证**；
- 人工评审是**角色扮演**，不代表真实部门批复。

## 明确不作为创新点宣传（仅作实现条件）

| 项 | 正确表述位置 |
| --- | --- |
| 大模型 / RAG | 技术实现章节，一句带过 |
| 知识图谱 | 作为语义层载体描述，不列为创新 |
| Nexent / MCP / 多 Skill | 工程编排方式，写进架构图即可 |
| 可视化页面 | Demo 手段，服务于"让评委看懂推演与证据" |

一旦把上述内容放进"创新点"页，评委的追问会立刻退化为"这和别人用 RAG 有什么区别"。

当前**不做也不宣传**的两项（避免叙事空转）：

| 项 | 为什么暂不做 |
| --- | --- |
| 多智能体协同进化（水务/交通双 Agent + 协同层） | 当前只有内涝单场景与两个片区，拆两个角色后局部反馈无法独立归因，"共同进化"没有可复算证据；等场景数与角色边界足够再上 |
| Progressive Skill Disclosure（按事件类型动态加载技能包） | 当前只覆盖内涝一类事件，没有"选错技能包"的场景，做出来只会是空演示 |

## 宣传语（统一口径）

> 提出一种面向城市基础设施突发事件的可演化语义数字孪生方法：通过多模态数据资产认知自动更新城市事件知识图谱，利用 Nexent MCP + Skills 编排跨部门因果推演，沿数据血缘追踪推理结果和处置建议的影响范围，并让稀缺资源分配策略在受控评测反馈下迭代进化。

## 30 秒答辩口径

1. 知识不是建完就静态：新公告进来，系统自己提出该改哪条关系、影响哪些历史结论，人确认后才发布，能回滚。
2. 推演不是列受影响清单：给的是暴雨→能力不足→积水→施工受阻→部门冲突→调整顺序的因果链，并且能回答"如果先封路会怎样"这种反事实。
3. 结论不是只有引用：数据一改，系统能说出哪几条历史结论、哪几条处置建议已经不可信，且只重算这一小部分。
4. 决策不是一次性的：抽水泵不够时先给谁，是一个有版本、可评测的策略；系统会从偏差里定位该改哪个信号（先封路阈值、再危险源），改了之后训练与留出偏差同时下降，改坏了门禁拒绝、随时回滚；同类场景第二次遇到时直接从分层记忆起步，领域负责人的修正会变成下一次的门禁约束。

## 30 秒答"进化是不是调参"（追问答辩口径）

1. 不是调模型：调的是**决策策略参数**（先保谁、能不能跨区调），推演结论是不可优化的输入。
2. 不是盲搜：每轮先做**偏差归因**，只改最差那一维对应的一个机制，一次只动一个参数组。
3. 不是只看训练集：候选只在训练集上选，**留出集门禁**要求不退化；人工评审结论作为**硬约束**。
4. 不是不可回退：每次采纳产出 `flood-response-v1.N` 标签，回滚后偏差逐位复原，两次运行结果一致。

## 答辩口径增补（多智能体 / 倒灌 / 定量层）

1. **多智能体不是口号**：1 总控 + 5 专业在协同板上出 24 张动作卡，每张卡都指向内核 claim 与证据；
   联合发布（道路 + 交通）缺一方即 `rejected`；处置顺序由规则裁决，Agent 不能把 C1/C2/C3 协商掉；
   `kernel_fingerprint` 把"这份协同方案对应哪一次推演"钉死，Agent 输出漂移不影响指纹。
2. **地下通道倒灌进推演**：外部积水 30cm 已漫过入口挡水槛 15cm → 跳 2 纳入、跳 5 增 1 台移动泵、
   跳 6 新增"封闭通道"且**序位 2**（不晚于封路）、二次风险新增倒灌（堰流量级 1.2 万 m³/h）。
   需求 7→8 台、缺口 1→2 台，全部对外数字已一次性重算并重新冻结。
3. **定量层让数字站得住**：产流 `Q=ψqF`、曼宁满流、积水提前量、堰流倒灌、区间/Monte Carlo、
   运筹松弛最优上界（证明进化后策略已达最优）、可靠性故障树（无备电 0.202、有备电 0.0201）、
   图论最小割封控、简化水动力演进（马斯京根汇流峰值削减/峰现滞后、修正 Puls 调蓄水位过程线）。
   每个数字都带公式、出处、假设与误差界；算不出来的显式声明，不编。
