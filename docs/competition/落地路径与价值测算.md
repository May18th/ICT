# 落地路径与价值测算

> 定位：回答「这东西谁会用、怎么接进去、值多少钱」。
> 原则：**不编数字**。凡本仓库拿不到的参数，一律标 `？` 并注明由谁提供。
> 数据真实性边界见 README 的分层表，本文不重复申辩「数据是真是假」，只讲落地。

---

## 一、先划清一件事：它替代的是哪一步人工

系统不是替代调度，也不是替代现场处置。它替代的是**「多方各自有依据、但没人能一次给出统一答案」的那两小时**。

具体到一次积水工单，人工现在的流程是：

1. 值班员接到积水上报，翻台账查设施型号与容量
2. 挨个打电话确认：泵站谁运维、路段谁管、燃气管道在不在开挖
3. 各部门拿着自己那份依据提方案，会上互相卡住（谁先封路、谁出泵）
4. 领导拍板，靠经验排序

系统的位置是在第 1 步到第 4 步之间：把台账、预案、交底记录一次性拉齐，输出**带出处**的六跳结论、
三类职责冲突的编号、稀缺资源缺口与处置顺序，并明确标出「哪些判断超出数据边界、必须现场确认」。

**所以买它的理由不是"更准"，是"两小时压到二十分钟，且每条结论能追到原文"**——
后者在事后复盘追责时才是真需求。

## 二、试点对象与切入顺序

按「数据可得性 × 决策痛点强度」排序，不按单位级别排。

### 第一站：区级排水（水务）主管单位

| 项 | 说明 |
|---|---|
| 为什么先来这里 | 他们手里已经有泵站 SCADA 和积水点台账，我们的设施实体能直接对上；不需要新建数据源就能跑 |
| 能提供什么 | 泵站运行状态、设计流量、养护单位；积水点历史工单；辖区内路段等级与易涝清单 |
| 缺什么 | 积水深度多为人工上报（照片/口述），无连续液位序列 |
| 我们替代哪一步 | 把「查台账 + 打电话确认运维主体」压成一次查询；把资源缺口算成「缺几台泵、从哪个片区调」 |
| 首期产出 | 一份带出处的推演报告 + 一份缺口清单，对着他们真实的月度工单跑 |

### 第二站：区应急管理局

| 项 | 说明 |
|---|---|
| 为什么排第二 | 跨部门协同是他们法定职责，但「谁先动」的排序一直是会议桌上谈的；这是本系统唯一别人难复制的部分 |
| 能提供什么 | 应急预案原文、成员单位职责清单、历史事件处置记录 |
| 缺什么 | 各部门实时资源位置（车/泵在哪），目前靠电话 |
| 我们替代哪一步 | 冲突识别与联合发布对：谁和谁必须同时发布才有效（例如封路需道路与交警联合），提前指出来 |
| 首期产出 | 一次桌面推演：拿历史事件重演，让各部门当场指出结论与他们的实际做法差在哪 |

### 第三站：市级防汛办（汇总层）

| 项 | 说明 |
|---|---|
| 为什么最后 | 市级要的是跨区汇总与全市态势，前置条件是下面两站已经跑顺、数据接口稳定 |
| 能提供什么 | 全市预警发布记录、跨区调拨规则 |
| 缺什么 | 区级数据的统一口径（同一个「积水深度」各区测法不同） |
| 我们替代哪一步 | 跨区调拨的优先级排序，以及「哪个区的缺口是真的缺、哪个只是没上报」 |
| 首期产出 | 横向对比表 + 口径差异清单 |

**顺序不能倒。** 先去市级会卡在「你们的数据口径和区里不一致」；先去应急局会卡在「设施状态我们不管，
你找排水」。第一站的账能对上，后面两站才有得谈。

## 三、数据接入清单

关键是把「已有系统能导出」和「需要新建台账」分开写。混在一起谈，试点一定延期。

### 3.1 已有系统，可直接接入

| 数据项 | 来源系统 | 接入方式 | 频率 | 我们用它做什么 |
|---|---|---|---|---|
| 泵站运行状态、机组启停 | 排水 SCADA | 定时拉取或数据库只读账号 | 分钟级 | 判断抽排能力是否被占用，算资源缺口 |
| 泵站设计流量、装机台数 | 资产台账 / 竣工资料 | 一次性导出为表 | 变更时更新 | 推演抽排时长 |
| 路段等级、车道数、是否易涝 | 道路管养系统 | 导出 CSV | 季度 | 封路范围与影响面 |
| 预案条款、部门职责 | 公开预案原文（已入库） | 已接入 | 年度修订 | 每条结论的出处引用 |
| 历史工单 | 12345 / 排水热线 | 导出 | 月度 | 复盘对照、策略评测的真实样本 |

### 3.2 需要新建或补齐

| 数据项 | 现状 | 建议采集方式 | 缺失时的影响 | 谁来决定 |
|---|---|---|---|---|
| 积水点连续水深 | 多为人工上报，无连续序列 | 液位计（重点点位先上）+ 视频识别（低成本补充） | 只能做**情景推演**，不能做实时校正；深度结论标注为「计算示意」 | 排水单位 + 财政 |
| 移动泵车/抽排车实时位置 | 电话调度，无系统 | 车载定位或司机端打卡 | 资源缺口只能按「账面可用台数」算，不知道实际在哪 | 应急局 |
| 各部门现场到场时间 | 无记录 | 处置流程里加一次打卡 | 无法量化「协同节省了多少时间」，价值测算只能给公式 | 应急局 |
| 地下管线施工计划 | 分散在各权属单位 | 按周汇总表 | 识别不出「积水 + 在施燃气/电力」这类叠加风险（本仓库最典型的冲突类型） | 住建 + 各权属单位 |

**这张表里「缺失时的影响」一栏比数据本身更重要。** 它把「我们做不到什么」提前说清楚，
避免试点三个月后被问「为什么你们算的水深和实测差这么多」。

## 四、价值测算

只给公式与口径。**参数本仓库不具备，需试点单位提供，不在本文写估算值。**

### 4.1 直接减少的损失

```
年减少直接损失 ≈ Σ(单次内涝直接损失 × 年发生次数 × 决策提前量折减率)

其中：
  单次内涝直接损失   = ？   ← 试点单位近三年灾损台账（财产险理赔 + 直接处置费用）
  年发生次数         = ？   ← 同一台账按「造成直接损失」口径筛选，不是所有积水工单
  决策提前量折减率   = ？   ← 试点期 A/B 对照实测（见 4.3）
```

### 4.2 节省的协同成本

```
年节省协同工时 ≈ 单次事件参与人数 × 单次会商时长 × 年事件数 × 压缩比例 × 人均工时成本

其中：
  参与人数 / 会商时长 = ？  ← 试点单位历史会商记录
  压缩比例            = ？  ← 目前只能给方向：把「查台账 + 逐个电话确认」从流程里去掉
  人均工时成本        = ？  ← 单位财务口径
```

### 4.3 折减率与压缩比例怎么测（试点期要做的唯一一件事）

这是整套测算的唯一实测入口，必须在前三个月做完：

1. 选 5–10 个历史事件，分两组：一组按原流程走，一组用系统出结论
2. 记录三个量：**决策形成时长**（从接报到方案定稿）、**结论被采纳比例**、**事后复盘时能追到原文的比例**
3. 第三个数是本系统最硬的指标——它不受「结论对不对」争议影响，只测「依据是否可核」

**没有这三组数，4.1 和 4.2 就只能停留在公式。** 本文不填估值，因为任何填入的数字都会在答辩现场
被追问「这个 30% 哪来的」，而答不上来比不填更被动。

### 4.4 不该算进价值的部分

- **减少的灾害损失不能全归系统**。预警提前量、工程改造、天气本身都在起作用，归因要做对照，否则数字虚高。
- **不能承诺"零漏判"**。数据边界表里已经写明哪些是示意值；承诺精度等于给自己挖坑。

## 五、推广路线与门槛

| 阶段 | 时间 | 交付物 | 通过标准（不通过就停） |
|---|---|---|---|
| 单点验证 | 第 1–3 月 | 对着真实工单出推演报告；完成 4.3 的对照实测 | 复盘时能追到原文；至少一个结论改变了当次处置顺序 |
| 单区铺开 | 第 4–9 月 | 接入 SCADA 与工单流；月度自动出缺口清单 | 值班员愿意日常打开，不是只在检查时打开 |
| 跨部门 | 第 10–18 月 | 应急局桌面推演常态化 | 冲突识别被部门认可（他们承认「这个冲突是真的」） |
| 市级汇总 | 18 月后 | 跨区对比与调拨排序 | 口径统一完成 |

**门槛写死在「通过标准」这一列。** 第一阶段的通过标准是「至少一个结论改变了当次处置顺序」——
如果系统出的结论每次都和人工一致，说明它没提供增量，这时候继续投钱是浪费。

## 六、答辩时可能被追问的三个问题

**Q：数据是合成的，凭什么说能落地？**
A：设施台账是按真实字段结构构造的，跑通的是**接口与判据**，不是数值本身。试点第一件事就是把
真实台账换进来——表结构不用改，这也是当初按真实字段建的原因。

**Q：和现有的指挥调度系统什么关系？**
A：不替代。现有系统管「指令下发与状态回传」，我们管「指令该下给谁、按什么顺序」。输出是给人看的
建议，不是直接下发的控制指令（我们没有控制回路，也不打算有）。

**Q：为什么不用大模型直接生成方案？**
A：做过对照——把工具解绑、提示词不变，模型会明确拒答「无法取证，不输出结论」；而绑上工具时
结论与离线推演逐项一致。也就是说方案的事实来自台账与预案，模型负责组织与解释。这条对照记录在
`docs/reports/nexent-live-evidence.md` 的对照组一节。
