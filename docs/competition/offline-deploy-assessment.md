# 离线部署评估（初赛提交物之一）

- 日期：2026-11-06
- 官方要求：作品须支持**离线部署包**，不能强依赖在线环境 `[官方赋能直播 14:38]`，来源见 [官方口径落库](official-brief-2026-11-06.md)
- 本文件性质：**评估，不是实施方案**。体积数字全是实测；裁剪可行性全部标注为「待验证」，未做任何验证就写"可以省"属于编造。

## 1 现状：能离线，但没打包

平台现在跑在本机 Docker（`nexent` 全栈 + `urban-twin-mcp` 共 17 个容器，已连续运行 4 小时），镜像全部来自在线拉取。断网后**无法从零重建**——没有 `docker save` 出来的 tar，也没有离线 compose。

## 3 三个可选裁剪点

### 3.1 sandbox（1.89 GB）——最有希望

`setup_nexent.py:96` 的 `DUTY_PROMPT` 已明确禁用 `python_interpreter` 与 `parallel_executor`，协同 Agent 同样禁用。也就是说**我们全链路不执行沙箱代码**。

- 待验证：停掉 `nexent-runtime-sandbox` 容器后，Agent 对话与 `event_deduce` / `collab_run` 是否仍全通（真机 8/8 复跑一次即可判定）。
- 若成立，离线包直接少 1.89 GB，且减少一个攻击面。

### 3.2 data-process（6.77 GB）——最大，但要看场景

我们的知识库是自建资产台账 + 本体，不走平台文档切分。若初赛材料不演示"上传文档建知识库"，这个容器可能不需要。

- 待验证：停掉后 Agent 配置页的"知识库"面板报错是否影响演示主链路。
- 风险：评审若追问"知识库能力"，不能答"我们没用"。建议**保留但在材料里说明用途边界**，而不是裁掉。

### 3.3 elasticsearch（2.05 GB）——中等

平台技能检索、知识库全文检索依赖它。若技能只靠 `name`/`description` 注入（当前事实如此，见台账考点③），ES 可能非必需。
- 待验证：停掉后技能仍然绑定、Agent 仍能对话。

## 4 两条路线

| 方案 | 做法 | 体积 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| **A 全量** | 全部镜像 `docker save` 成一个 tar + 离线 compose + 安装脚本 | ~17.5 GB（压缩后待实测） | 一小时能做完，风险最低 | 分发成本高；评委下载不友好 |
| **B 裁剪** | 按第 3 节裁掉 sandbox（+可选 ES），其余全量 | 约 15.6 GB | 证明"我们真的做过离线适配" | 每个裁剪点都要真机验证，任一不通就回退 |

建议：**A 打底、B 作为加分**。先按 A 出一份能跑的离线包（保底满足硬要求），再用 3.1 的 sandbox 裁剪做一次"离线最小集"验证，作为"我们做过离线适配"的具体证据。

## 5 实施清单（若开工）

1. `docker save` 关键镜像 → `offline/images/*.tar`，逐个记 sha256；
2. 离线 compose：把 `deploy/` 下现有 compose 的 `image:` 改为本地 tar 加载后的标签，去掉 `build:` 段；
3. `install.sh`：`docker load` 全部 tar → `docker compose up -d` → 健康检查（`/nb/v1/health` + `urban-twin-mcp` 的 `/health`）；
4. **断网实测**：拔网线/断 WLAN，从零起一遍，跑一次六跳对话，截图留证；
5. 写 `OFFLINE.md`：资源需求（官方口径 4 核 16G 起步，本机实测见下）、端口占用、常见失败（镜像标签不一致、卷权限）。

## 6 本机实测参照（写材料可引用）

- 17 个容器连续运行 4 小时无重启，`supabase-db-mini` / `urban-twin-mcp` / `elasticsearch` 均 healthy；
- 平台入口 `http://localhost:3000`（返回 307 跳转正常），管理 API `http://localhost:5010`（导出接口实测 200）；
- 官方口径：做数据处理至少 4 核 16G，内存不足会导致文件处理失败 `[直播 10:26]`。

## 7 结论

- 硬要求「支持离线部署」**当前不满足**：能离线运行，但无法离线重建。
- 最小可行交付是方案 A（全量 `docker save` + 离线 compose），工作量约半天，主要成本是体积与断网实测。
- 方案 B 的 sandbox 裁剪有充分依据（我们本来就禁用沙箱执行），值得做一次验证；data-process 与 ES 建议保留、在材料里说明用途边界，不要为了减体积冒演示失败的风险。
