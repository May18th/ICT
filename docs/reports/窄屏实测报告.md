# 窄屏实测报告

> 实测时间：2026-11-17
> 被测服务：本地 `decision_poc.web_demo`（127.0.0.1:8901），代码为**当前工作树**。
> （工作树里同时有另一路会话在改页面文案——「它会错吗」改为「能力边界与已知误差」等，
> 均不涉及布局，对本文结论无影响。）
> 浏览器：Edge 157 headless（`--headless=new`，`--hide-scrollbars`）
> 结论：**`/map2d` 与 `/data` 在 414px 及以下不可用，`/workbench` 在 375px 及以下整页横向溢出。**
> **`/evolution` 与首页在全部测试宽度可用**——前者已经把表格放进可横向滑动的卡片里，
> 是这套代码里唯一处理过窄屏的页面，可以当参照。

---

## 一、怎么测的

不靠数 `@media` 断点推断，直接量真实布局。

1. 起服务：`.venv/Scripts/python.exe -m decision_poc.web_demo --port 8901`
2. 起同源转发：`artifacts/proxy_measure.py`（`/measure` 出测量页，其余透传给 8901）。
   必须同源——跨端口就是跨域，父页读不到 iframe 的 `contentDocument`，拿不到布局。
3. 测量页用 `<iframe>` 逐个加载目标页，宽度分别设为 320 / 375 / 414 / 768 / 1280，
   页面的 `@media` 按 iframe 宽度生效。每个组合等待 1.4s 后读取：
   - `documentElement.scrollWidth` vs `clientWidth`（是否**整页**横向溢出）
   - 所有元素 `getBoundingClientRect()`，记 `right > clientWidth + 2` 或 `left < -2` 的
   - **每个溢出元素再往上找最近的滚动祖先**（`overflow-x` 为 `auto`/`scroll`），
     记下它是否能滚（`scrollWidth > clientWidth`）。这一条是关键：
     元素超出视口但在可滚容器内 = 用户能滑到，不是破版
   - `body` 计算字号、SVG 的 `viewBox` 与实际 CSS 宽度
4. 截图：`msedge --headless=new --window-size=W,812 --screenshot=...`

复现命令（两步）：

```bash
cd /d/华为ICT/agent_poc
# 1) 起演示服务（换个没被占用的端口）
.venv/Scripts/python.exe -m decision_poc.web_demo --port 8901 &
# 2) 一条命令量完 5 页 × 5 宽，自动驱动 headless 并落盘
.venv/Scripts/python.exe scripts/measure_narrow.py --target http://127.0.0.1:8901
```

脚本会自己找 Edge/Chrome、起同源转发、跑 headless、解析结果并打印汇总表，
同时写 `docs/reports/narrow-measure.json`。没有浏览器时用 `--serve-only` 手动打开测量页。

原始数据：`docs/reports/narrow-measure.json`（25 组记录，含每个溢出元素的选择器、`left`、
宽度、文本片段）。

## 二、结论矩阵

`scrollW` 是文档实际宽度，`clientW` 是可视宽度。两者不等 = **整页**出现横向滚动条。
「卡内可滚」是另一回事：元素超出视口，但最近的祖先设了 `overflow-x:auto` 且能滚，
用户可以横向滑动看到全部内容——这不算破版。

| 页面 | 320 | 375 | 414 | 768 | 1280 |
|---|---|---|---|---|---|
| `/` 门户 | 可用 | 可用 | 可用 | 可用 | 可用 |
| `/evolution` | 卡内可滚 | 卡内可滚 | 卡内可滚 | 可用 | 可用 |
| `/workbench` | **整页溢出 83px** | **整页溢出 28px** | 可用 | 可用 | 可用 |
| `/map2d` | **地图 4px 宽** | **地图 59px 宽** | **地图 98px 宽** | 勉强 | 完整 |
| `/data` | **整页溢出 202px** | **整页溢出 147px** | **整页溢出 108px** | 可用 | 可用 |

> 表中 `/data` 在 768/1280 出现的两处「超出视口」是 SVG 画布内的 `path` / `g`
> （地图图层）。SVG 裁剪超出 viewBox 的内容是画布的正常行为，不计入破版。

## 三、逐条给根因：两处破版 + 一处已处理

### 3.1 `/map2d`：右侧面板固定 316px，把地图压成一条

测量值：

| 视口 | 地图 SVG 实际宽度 | 推算 |
|---|---|---|
| 320 | 4px | 320 − 316 |
| 375 | 59px | 375 − 316 |
| 414 | 98px | 414 − 316 |
| 768 | 452px | 768 − 316 |
| 1280 | 964px | 1280 − 316 |

**每个宽度都精确等于「视口宽 − 316」。** 根因在 `scripts/build_map2d.py`：

```css
#side{width:316px; ... flex-shrink:0}
```

右侧「当前态势 / 决策调配 / 跨部门协作」面板宽度写死 316px 且 `flex-shrink:0`，
不收缩、不换行。地图（`flex:1`）只能吃剩下的空间。

更关键的是**断点里没有单列化**：

```css
@media(max-width:1200px){#agentlog{display:none}}
@media(max-width:1400px){#dock .hint{display:none}}
@media(max-width:1440px){...}
```

三档断点全是宽屏微调（隐藏日志面板、隐藏提示语），**900px 以下没有任何规则**。
也就是说这个页面从设计上就没考虑过手机。

连带后果（同一次测量里 12 个溢出元素）：

- `span#ly-time` / `span#ly-model` / `span.ly-ledger` 这些**数据来源 chip 的 `left` 值在 802~860px**，
  视口只有 320~414，全在屏幕外。而这三枚 chip 是「数据边界展示」的核心（台账 / 模型估算 / 时间线），
  评审最关心它们，手机上恰好一个都看不到。
- 字幕块在窄屏竖排成柱状，直接盖住本已只剩 59px 宽的地图——见截图 `map2d-375.png`。

对比 `map2d-1280.png`：1280 下地图占主体、右侧面板正常、字幕横排在底部，是完全可用的专业大屏。
**这不是设计失败，是缺少窄屏分支。**

### 3.2 `/data`：两列网格没有单列断点，被 427px 宽的图撑开

```css
main{padding:6px 40px 34px;display:grid;grid-template-columns:1fr 1fr;gap:16px;max-width:1480px}
section.wide{grid-column:1/-1}
```

`1fr 1fr` 在 320 宽下每列理论 152px，但 `section` 内部有个 SVG 实际宽度 427px 且不收缩，
撑破列宽后整个文档 `scrollW` 固定为 507（320/375/414 三个宽度都是 507，说明是**某个固定
宽度的内容**在决定，与视口无关）。

这个页面全篇没有 `@media` 单列规则——翻遍 `<style>` 只有宽屏定义。

### 3.3 `/evolution`：这个页面做对了，可以当参照

先记一笔自我更正。第一版测量把这张表判成「被裁死」，是因为脚本只比较元素右边界与视口宽度，
没有继续往上找滚动容器。补上滚动祖先检测后，结论反了：

| 视口 | 表格实际宽 | 最近滚动容器 | 容器可视宽 | 能否滑动 |
|---|---|---|---|---|
| 320 | 654 | `section.card.evolution-card` | 280 | **能** |
| 375 | 654 | 同上 | 360 | **能** |
| 414 | 654 | 同上 | 399 | **能** |

根因在 `evolution_demo.py` 的两行：

```css
@media(max-width:900px){ ... .evolution-card{overflow-x:auto} ... }
@media(max-width:560px){ ... table{min-width:620px} }
```

分工很清楚：**560 以下不让表格被压扁**（强制 620 宽），**900 以下让卡片接管横向滚动**。
两者接上，用户在手机上横滑卡片就能看全右侧列。

这套写法就是另外两页缺的东西：不是「加断点」，是「先决定谁负责滚动」——
表格保持可读的最小宽度，由最近的卡片当滚动宿主。

顺带说明：`web_demo.py:1256` 那处 JS 生成的表格早就包了 `overflow-x:auto`，
说明团队里有人踩过这个坑，只是没把它推广到别的页面。

### 3.4 `/workbench`：面板最小宽度撑破 320

`section.panel` 实际宽 370px（320 视口下 `left=18`，`right=388`，溢出 83px）。
12 个元素连坐：`.switch` / `.hint` / `#chatpane` / `#feed` / `.askbar` / `#f` / `.tabs`。

`workbench-320.png` 里能看到右侧被硬切：标题「结论可定位原**文**」的「文」贴着边，
输入框和 tab 条都越界。

`web_demo.py` 的 `@media(max-width:960px)` 和 `@media(max-width:640px)` 覆盖了
`main` padding、`primary-grid`、`#metrics`、`.guide`，但**没有覆盖这块面板的固定宽度**。

## 四、修复方向（本次只诊断，未改代码）

**先定原则，再谈改哪行**：`/evolution` 已经给出这套代码的正确解法——
「内容保最小可读宽度，最近卡片当滚动宿主」。`/data` 和 `/workbench` 照抄这个思路即可，
不需要发明新写法。

| 优先级 | 改动 | 落点 | 风险 |
|---|---|---|---|
| P0 | `/map2d` 加 900px 以下断点：`#side` 改为 `width:100%` 且 `flex-direction:column`，地图 `min-height:52vh` | `build_map2d.py` 样式段 | 中——动了布局要和 `applyCam`/`scaleLabels` 的屏幕补偿一起复测 |
| P1 | `/data` 加 `@media(max-width:760px){main{grid-template-columns:1fr}}`；`section` 内 SVG 容器 `min-width:0`，表格改「保宽 + 卡片滚动」 | `web_demo.py` data 页样式 | 低 |
| P1 | `/workbench` 面板 `min-width:0`，窄屏 `main` padding 收到 12px | `web_demo.py` workbench 样式 | 低 |
| P2 | `/map2d` 顶部 chip 行窄屏改两行或横向滚动容器 | `build_map2d.py` | 低，但 chip 是数据边界证据，优先保证可见 |
| — | `/evolution` 无需改动 | — | 已处理 |

**P0 那条不要单人改**：`scaleLabels()` 按 `(vb.w/880)^0.6` 做字号补偿，`CAM_FRAMES` 按字幕
时间轴对齐，改布局要重跑全流程截图核对。

**建议的第一个改动是 `/workbench`**——它只有两个值要动（面板 `min-width:0`、窄屏 padding），
改完用 `scripts/measure_narrow.py` 复测一遍就能确认，是最低成本的验证点。

## 六、这次实测否认的三个说法

1. **「做了 7 档断点，所以响应式没问题」** —— 断点数不等于覆盖度。`web_demo.py` 那 7 档
   确实存在，但它们分布在三个不同页面的三套独立 `<style>` 里，`/map2d` 一套、`/data` 一套、
   `/workbench` 一套，互不共享。`@media` 写在 A 页面不会救 B 页面。
2. **「3D 已停用，前端就是普通网页，手机上应该还行」** —— `/map2d` 是单文件 SVG 大屏，
   它的布局假设是横向 ≥1200px 的投影仪。手机上不是「有点挤」，是地图只剩 4~98px。
3. **「元素超出视口就是破版」** —— 错，要看它上面有没有可滚容器。本报告第一版就是因为
   少了这一步，把 `/evolution` 判成死版，结论完全反了。**这条教训对后续维护更值：
   判断「能不能用」要同时看「有没有人负责滚动」，只量元素边界会系统性地高估问题。**
