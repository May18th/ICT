## 1. 反事实怎么算：干预输入 → 重建 → 重放 → 取 diff

一句话：**不改代码，改世界，然后用同一套规则重跑一遍，比结论。**

| 手段 | 改什么 | 用在哪 |
| --- | --- | --- |
| `data_patch` | 数据集某一行某一列（库存数量、完工时间） | CF2、CF3 |
| `rule_patch` | 规则的一个参数（处置顺序 `then.order`） | CF1 |

为什么不是"改逻辑再跑"：改代码的两条分支不再共享同一套规则，diff 出来的差异就不再是"干预造成的"，而是"代码差异造成的"，无法复核。

落地细节：

- 数据补丁在临时目录里改副本，`shutil.copytree` → 改 CSV → 用副本重建 runtime；**样本数据一个字节不动**（有测试比对 sha256）。
- 补丁必须唯一命中一行，命中 0 行或 2 行直接报错——"改到了不该改的行"比"没改"更危险。
- 规则补丁写临时 JSON，仍然走 `verify_rules` 的原文行校验，所以改完规则的出处依然可查。
- 分支跑 `persist=False`，不写溯源账本：反事实是推演，不是对外结论。

## 2. 三个用例的实测

### CF1：若先封路再隔离风险源

```
基线:   动作 9 项 / 冲突 3 项 / 缺口 1 / 可发布 是
反事实: 动作 9 项 / 冲突 3 项 / 缺口 1 / 可发布 是
  顺序: 封闭积水路段全幅… 第 3 → 第 2 位
  顺序: 封路由 ORG-ROAD 与 ORG-TRAFFIC 联合发布… 第 4 → 第 3 位
  顺序: 隔离风险源… 第 2 → 第 4 位
道路可通行性:
  R-101 兴华路: 封闭
  R-102 建设大道: 可通行
  R-103 民生街: 受施工影响
  R-104 环城北路: 可通行
  R-105 兴华支路: 受施工影响
通行代价（自由流，不含路口延误）:
  封 R-101 使 J-01→J-02 从 820 m / 1.2 分钟 变为 3860 m / 6.3 分钟（绕行 +3040 m，+5.1 分钟，经 R-102/R-103/R-104）
  基线路径: J-01→J-02 经 R-101，820 m，1.2 分钟
  封路后路径: J-01→J-02 经 R-102/R-103/R-104，3860 m，6.3 分钟
结论: 封路由第 3 位提前到第 2 位，隔离风险源由第 2 位后移到第 4 位；封路后可通行道路为
      建设大道、环城北路；受限道路 兴华路(封闭)、民生街(施工)、兴华支路(施工)；
      封 R-101 使 J-01→J-02 从 820 m / 1.2 分钟 变为 3860 m / 6.3 分钟（+5.1 分钟，经 R-102/R-103/R-104）。
无法计算的部分:
  ! 门到门到场时间：缺抢修驻地坐标与实时路况，只算到路口之间的通行时间
  ! 跨区路径：A-03 与 B-01 的路段之间没有连接数据，跨区调配只有台账里的 40 分钟
```

**"慢多少"现在是算出来的，但仍然只算到该算的地方。** `road_network.csv` 补了 `from_node/to_node/speed_kmh/work_zone_factor` 之后，封路就是图上删一条边，绕行就是 Dijkstra 的另一条路径：J-01→J-02 从 820 m/1.2 分钟变成 3860 m/6.3 分钟，路线固定为 R-102→R-103→R-104。三个口径写在 `road_graph.py` 的模块注释里：

1. **自由流**：时间是 Σ(长度 ÷ 有效速度)，不含路口延误与排队——没有这些数据就不猜；
2. **占道降速写在数据里**：`R-103` 是被公告指定的绕行路，本身在占道施工（CP-2026-038），降速系数 `0.5` 与这条路同处一行，不是代码常数；
3. **断网就是断网**：三条路同时断时 `route()` 返回 `None` 并标 `cut=True`，不返回一个很大的数字冒充"很慢"。

门到门到场时间仍然算不出（缺驻地坐标与实时路况），跨区路径也算不出（两片区之间没有路段连接数据）——这两条照旧进 `uncomputable`。

### CF2：若抽水泵只有 2 台

```
基线:   动作 9 项 / 缺口 1 / 库存 6
反事实: 动作 9 项 / 缺口 5 / 库存 2
  缺口: RES-PUMP-M +4 台
片区优先级:
  A-03 (WO-20261029-007) 深度 30cm 封路 是 危险源 有 需 5 台 / 本区 2 台 / 缺口 3
  B-01 (WO-20261029-011) 深度 18cm 封路 否 危险源 无 需 2 台 / 本区 0 台 / 缺口 2
  · A-03 积水 30cm，已过封路阈值（阈值 25cm）
  · A-03 受影响范围含燃气/电力管线，存在次生风险
  · B-01 积水 18cm，未过阈值，且无次生危险源
  · RES-PUMP-M-B01: 单台 400 m3/h，跨区调用需 40 分钟
结论: 抽水泵 6 台 → 2 台，缺口 1 台 → 5 台；A-03 需 5 台（本区 2 台，缺 3）、
      B-01 需 2 台（本区 0 台，缺 2），优先保障 A-03…
```

**优先级不是写死的，是跑出来的。** 两个片区各跑一遍完整推演，比较四个量：是否过封路阈值、是否含次生危险源、积水深度、动作条数。A-03 两项命中，B-01 全不命中。

跨区代价直接引用 `resource_inventory.csv` 的 `capacity_note`（"跨区调用需 40 分钟"），附证据定位，不是凭经验补一句。

**需求与本区库存都按片区归集。** 原来 `RULE-RES-LOWSPOT-PUMPS` 的算法是"其他片区 × 2 处低洼点 × 1 台"，于是同一个 B-01 从 A-03 的视角看是"替 A-03 备的 2 台"，从 B-01 自己的视角看又不算自己的低洼点——两片区独立推演时总量不能相加。现在改成两件事：

1. 每个片区只按自己的对象算一次需求（A-03 泵站补位 3 + 基坑 2 = 5；B-01 低洼点 2 × 1 = 2），`demand_by_district` 可相加也可单取，合计仍是 7 台；
2. 低洼点临时抽排的适用条件从"是不是本片区"改成"该片区积水是否达到封路阈值"（阈值读 `RULE-ACT-CLOSE-ROAD` 的 25cm）：B-01 18cm 计 2 台，A-03 30cm 已过阈值，走泵站补位与基坑排水，不叠加低洼点台数。

有一条测试专门守这个口径：`test_district_demand_does_not_depend_on_which_district_is_primary` —— 同一片区换视角推演必须得到同一个数。

### CF3：若 CP-2026-041 延期一天

```text
基线:   动作 9 项 / 冲突 3 项 / 缺口 1 / 可发布 是
反事实: 动作 9 项 / 冲突 3 项 / 缺口 1 / 可发布 是
  + 风险: 开挖面暴露期与红色预警窗口重叠：按预案响应分级应启动全区响应…
  - 风险: 开挖面暴露期与橙色预警窗口重叠：按预案 4.2 该期间应停止开挖并覆盖或围堰…
  暴露: orange 6h → red 12h
结论: 开挖面暴露期与预警窗口的重叠等级由 orange 上调为 red（重叠 6h → 12h）；
      新增二次风险：开挖面暴露期与红色预警窗口重叠。
无法计算的部分:
  ! 超出预警发布时效的工期无法判断：气象侧只有到 10-30 12:00 的预警，更远期无数据
```

动作与缺口一条没变，**变的只有"开挖面暴露多久、撞上多强的预警"这个量**，二次风险随之从橙色档升到红色档。这正是 ground truth 期望的"风险等级上调"。

#### 补之前它长什么样（这段决定了我怎么补）

第一版 CF3 的结果是"无差异"。系统扫了规则条件，确认没有任何日期字段参与判定，于是如实回答"当前知识回答不了"，并列出缺什么。**当时没有编"风险等级上调"**——编了就是标准的幻觉：既没有规则支撑，也没有次日气象数据。

补的时候只动了两处，推导逻辑一行没改：

1. **数据**：`weather_alerts.csv` 加 `WA-20261030-01`（10-30 06:00–12:00 红色预警，`issued_at` 10-29 06:00 提前发布）。因为有效期在未来，今天 09:40 的观测跳取不到它——这条有测试守着（`test_future_warning_never_leaks_into_todays_observation`），否则"提前发布的预警"会变成"今天就是红色"的泄漏。
2. **规则**：两条 `residual_risk` 规则，条件是 `pit_exposed_warning_level`（暴露期与同片区预警窗口重叠后的最高等级），分别对应 orange / red。出处是预案 4.2（第 38 行"停止开挖作业"）与响应分级（第 25 行"全区响应"），仍由 `verify_rules` 逐行核对关键词。
3. **引擎**：新增 `_warning_exposure()`，用**区间重叠**判断工期覆盖了哪些预警窗口。用"此刻是否生效"永远只能看到当下，看不到明天——这是开工时间与完工时间要分开处理的原因。

顺带修了一个语义错误：更早一版把"延期"实现成开工推迟一天，结果今日基坑直接不存在，结论大变（少 3 个动作、危险源消失、缺口 −1）。那是"推迟"，不是"延期"。

## 3. 接进 MCP：第 8 个工具

```
counterfactual_run(case_id, event_id, as_of, caller_labels)
```

放进 MCP 而不是只留 Python 接口，因为 Demo 要现场回答"如果……会怎样"；只留进程内函数，P7 只能演假交互。

一个关键判断：**基线本身算不出来时不回"空差异"。** 空差异会被读成"没有影响"，这与"算不出来"是两件事，但两者在展示层长得一模一样。

这个判断放在核心 `run_counterfactual()` 里（抛 `CounterfactualUnavailable`），不是只在 MCP 层挡一道。原因是第一版只加在 MCP 上，CLI 走同一路径时照样返回"差异：无（结论层面完全一致）"——同一条安全规则两个入口两套行为，等于没做。

现在的行为：

| 情形 | 结果 |
| --- | --- |
| 基线 `PERMISSION_DENIED`（如 `ORG-ROAD` 看不到燃气规程） | 拒绝比较，MCP 回 `PERMISSION_DENIED`，CLI 打印后退出码 2 |
| 基线 `EVIDENCE_INSUFFICIENT`（如审计闸门拒绝） | 拒绝比较：不可发布的结论不足以做基线 |
| 未知用例 | `NOT_FOUND`，回可选值 `["CF1","CF2","CF3"]` |
| 重放过程异常 | `EVIDENCE_INSUFFICIENT` |

注意区分：基线**降级**（如缺深度导致 `partial`）仍允许比较——那是有效的、只是不完整的基线，正好是反事实该处理的场景；只有 `error` 才拒绝。

`skill_manifest()` 升到 1.1，新增 `standalone_tools`：反事实不是链路中的一跳，而是对已发布结论的追问，所以不进 `SKILL_ORDER`，由编排层在拿到基线结论后直接调用。绑定表里的工具名仍由测试对着 `UrbanToolkit.tools()` 校验。

## 5. 结论只由算出来的量拼装

`_verdict()` 里的每个数字都来自 diff、分支汇总或数据表，没有任何一句"通常会……"。这条规则不是为了好看：**一旦允许一句解释性文字，它就会成为整套可验证性里唯一无法验证的部分**，而答辩恰恰专挑这种句子问。

三个用例的 `uncomputable` 字段把所有算不出来的部分显式列出，和结论一起返回。

## 6. 遗留（P8 之前）

1. **CF3 的时效边界**：现在只能判断到已发布预警的覆盖范围（10-30 12:00）。工期再往后延，就超出气象数据时效，`uncomputable` 会照实说——要答更远期的问题，需要接入逐日预报。
2. **CF1 的门到门与跨区**：路口之间的通行时间、绕行里程、绕行路线已经能算（`road_graph.py`），但"车从驻地到现场"还缺驻地坐标与实时路况；跨区路径缺 A-03 与 B-01 之间的路段连接，只能引用台账里的 40 分钟。
3. **低洼点口径已统一，规则本身仍是演示假设**：`RULE-RES-LOWSPOT-PUMPS` 的"每片区 2 处低洼点 × 1 台"没有原文依据（`assumption=true`），现在至少按片区各算一次、条件也明确挂在封路阈值上；真要上生产，得让排水公司给每个片区的低洼点台账。
