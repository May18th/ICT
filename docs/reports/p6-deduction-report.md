## 2. 规则为什么是数据，以及"可验证"到什么程度

`DeductionRule` 只有 `when` / `then` / `priority` / `source_ref` / `keyword` 五个关键字段。加载时逐条做三件事：

1. `source_ref` 拆成 `<file_name>#<locator>`，按 locator 取原文行；
2. 断言该行**真的包含** `keyword`；
3. 解析出资产 `asset_id`，拼成 `asset_id#locator` 作为可入账的证据引用。

任一条不满足就抛 `RuleSourceError` 并列出全部问题，不是警告。理由很直接：一条规则如果指不到原文，它就不是"依据偏弱"，而是**错的**。

实测 26/26 通过。反例测试两条：把 keyword 改成原文没有的句子、把行号改成 9999，都按预期拒绝加载。

`source_ref` 用**文件名**而不是 `asset_id`：`asset_id` 是内容寻址的，改一个字符整份文件换 id，规则会集体失效；文件名稳定，而资产 id 在加载时现算。

## 3. 两条被显式标注的假设

推演里有三个数字没有原文依据，我没有把它们伪装成规则输出：

| 规则 | 假设内容 | 原文只说了什么 |
| --- | --- | --- |
| `RULE-RES-PIT-PUMPS` | 每处基坑抽排需 2 台移动泵 | 预案 §4.2 要求基坑覆盖/围堰与 2 小时一次检测，未给泵数 |
| `RULE-RES-LOWSPOT-PUMPS` | B-01 两处低洼点、每处 1 台 | 台账只有"积水 18cm 未达阈值" |

两条都带 `assumption: true` + `assumption_note`，并出现在结果的两处：`result.assumptions`（展示用）和 `handoff_reasons`（触发转人工）。

这么做是为了答辩时能直接说清：哪些是文件规定的，哪些是演示需要现场核实的。混在一起讲，被追问一次就站不住。

## 5. 证据链：从推演到可审计的记录

`claims_from(result)` 把每一步转成 `Claim`，规则刻意保守：

- 有 **≥2 条不同出处** → `inference`，前驱引用被当前引用包含时才挂前驱；
- 单出处且有规则 → `rule_output`（账本会校验规则 `source_ref` 可定位）；
- 单出处无规则 → `fact`；
- `insufficient` 的跳不生成 claim —— 没结论就不该有账。

实测 14 条 claim 全部通过 `register()`，无一条 `unsupported`，`record()` 落账后 `verify()` 为 True。`trace_claim("CL-S6-action-02")` 能取回规则 id、规则出处 `…emergency_plan/v2.0#line:31` 与证据 locator。

**"引用完整率 100%"在这里是可断言的事实，不是统计口径。**

## 6. 这一轮修掉的五个问题

1. **语义层把排水分区当行政片区**：`region_id` 之前取 `district or drainage_zone`，导致 `DF-PS-01` 的"片区"是 `DZ-01`，按片区查设施全部落空。改为只认 `district`，排水分区留在属性里。这条是 P4 留下的建模错误，P6 一用就暴露。
2. **施工项目被当成"职责空白"**：运维责任只对实物资产成立，施工项目有施工方与许可方。加了 `maintainable` 集合白名单，否则 C2 会多出 `CP-2026-041`。
3. **C1 检不出**：职责表里 ORG-ROAD 写的是"封闭道路实施"、ORG-TRAFFIC 写的是"封路审批"，单关键词 `封路` 只能命中一个。改成关键词列表 + 并入图上已有的 `conflicts_with` 三元组双路取证。
4. **冲突编号重复**：按插入顺序编号导致两个 C3。改为先按类型排序再统一编号。
5. **`main()` 定义在 `if __name__` 之后**：脚本模式下 `build_rule_registry` 还没定义就调用。入口统一移到文件末尾。

## 7. 规则缺失时的两种行为（刻意区分）

| 情形 | 行为 | 理由 |
| --- | --- | --- |
| 条件不匹配（如深度 8cm 不达任何分级阈值） | 该跳 `insufficient`，推演继续，结论降级 | 这是真实业务里的"规则没覆盖"，必须让人看见 |
| 引擎必需的参数规则缺失（如折算系数） | 构造期抛 `RuleSourceError` | 这是配置错误，跑出一份缺系数的推演比不跑更危险 |

`REQUIRED_RULE_IDS` 列出 7 条引擎按 id 取参数的规则，缺一条就不让建引擎。

## 8. 已知边界

1. **Skills 层未做**：P6 标题里的"5 个 Skill 的输入输出与工具编排"没有落地。当前只有 MCP 工具 + 推演引擎，Skill 编排属独立一层。
2. **反事实未实现**：CF1/CF2/CF3 需要"同一套规则重放 + 干预后 diff"，引擎已具备重放能力（确定性输出），但干预接口没写。
3. **面积条件无数据**：预案 §3.1 是"深度 ≥25cm **或** 面积 ≥200m²"，工单里只有深度。规则用 `or_` 前缀表达析取，面积分支因无字段恒不满足——这个"缺一个分支"的事实目前没有体现在输出里，容易让人误以为两个条件都验过了。
4. **受影响范围偏宽**：同一条路上的所有管线都会进范围（`PL-PWR-101` 即如此）。相对 ground truth 是超集，对"影响范围"这类问题宁多勿少，但做资源测算时会把无关管线也算进去（当前只算泵站与基坑，尚无影响）。
5. **`handoff_required` 只是信号**：没有工单系统可对接，转人工停留在字段层面。
