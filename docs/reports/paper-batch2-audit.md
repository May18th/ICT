## 1 核实口径

「可获取」的判定标准是**能否逐字取到原句**，不是页面能否打开：

| 步骤 | 做法 | 判定 |
|---|---|---|
| ① 取页/取 PDF | 直连 HTTP（带桌面 UA），记录状态码、content-type、字节数 | 200 + `application/pdf` 或正常 HTML 才算到站 |
| ② 取文本 | `pypdf` 逐页提取文本层 | 提取字符数 > 0 才算有正文 |
| ③ 定位原句 | 全文合并断行后做子串查找，记录命中页 | 命中才可写入摘录卡 |
| ④ 术语计数 | 合并断行后按不同写法分别统计（如「级联」「连锁」分开计） | 用于判断文献实际重心，替代摘要印象 |

页码口径：

- P0-1：刊页 1218–1232，PDF 第 1 页 = 刊页 1218；
- P0-4：刊页 1–16，PDF 第 n 页 = 刊页 n；
- P0-2：PDF 页序（首页为摘要页，页码以 PDF 计）。

文本说明：PDF 文本层的中文含断行与全角空格，摘录卡中的原句为**合并断行、压缩空白**所得，**未改字词**。这一点决定了未来若要把摘录卡注册为 `source_ref` 载体，必须先做逐字清洗核对（§6）。

## 3 三处纠偏

### 3.1 P0-4：内容重心与「部门关系、资源争用」不符

对 46 525 字全文做术语计数（合并断行后）：

| 术语 | 出现次数 | 说明 |
|---|---|---|
| 交通 | 19 | 多为致灾对象与疏散研究 |
| 脆弱 | 11 | 网络脆弱性指标 |
| 部门 | 7 | 基本是政策背景句（如「跨地域、跨部门的系统工程」） |
| 演化 | 6 | 灾害链演化 |
| 协同 | 5 | 多为「学科协同」「协同分析」 |
| 级联 | 3 | 级联失效 |
| 关键节点 | 2 | 中心性识别 |
| **依赖** | **0** | 无设施依赖关系建模 |
| **调度** | **0** | 无资源调度 |
| **资源配置** | **0** | 无资源分配 |
| **博弈** | **0** | 无多主体博弈 |

这篇综述的实际重心是**网络拓扑指标（度分布、介数中心性）+ 灾害风险指标 + 灾中非线性行为（含级联失效与灾害链演化网络）**，属于「用什么指标刻画关系网络」的方法层，不是「谁该负责、资源怎么分」的管理层。

因此原表中「支撑设施依赖、部门关系、资源争用和灾害级联关系的建模依据」应改为：

> 支撑**设施网络拓扑关系、关键节点识别、灾害链演化建模**；不支撑部门职责边界与资源争用规则。

本项目的部门关系与资源争用仍只能靠台账（`duty_list.csv`、`resource_inventory.csv`）与规则 `RULE-RES-*`，文献给不了这一层。这一点与既有审计 §4 的判断一致：①源头减排、③蓄排调节缺的是工程量与费用口径，不是分类法。

### 3.2 P0-1：方法链不可整搬（LDA/LTP/舆情数据）

原文方法链（刊页 1219–1220）：

```
LDA 主题建模 + LTP → 16 万条社交媒体数据 → 6 类高频舆情主题
        ↓
覆盖内涝灾害全周期的领域本体与知识图谱
        ↓
12 类基础地理场景 + 39 类应急管理场景的「知识-要素映射表」
        ↓
面向多类型用户的按需场景模拟（原型系统）
        ↓
115 份有效问卷验证：交互便捷性 4.06 / 运行效率 4.09 / 功能完备性 4.07（满分 5）
```

可借的是**结构**：分层本体 → 映射表 → 按需呈现，三层分离且每层可单独核对。
不可借的是**数据与方法**：本项目没有社交媒体数据源，LDA/LTP 无输入；照搬会在答辩现场被追问「16 万条舆情在哪」。

另一个落点问题：`ontology_bootstrap` 的种子是设备检修域（10 类型 / 11 谓词：`Equipment`、`Line`、`FaultMode`、`ThresholdRule` 等），与「预案-要素」不是同一套类型系统。P0-1 真正对位的是：

| P0-1 的概念 | 本项目承接物 |
|---|---|
| 预案知识节点 | `rules.source_ref`（`plan_flood_emergency_v2.md#...line:N` + `keyword`） |
| 场景要素 | `samples/assets/urban/` 19 项台账 + `scene.json` 语义真源 |
| 要素与实体的实例化映射 | `scene_binding`（`TW-*` 主键对齐） |
| 按用户类型裁剪 | 门户四入口（系统概览 / 推演流程 / 证据依据 / 能力边界） |

### 3.3 P0-2：五段里「救援」本项目无对应

原文为「预案—监测—推演—协同—**救援**」五段，配五方面应对方法（完备综合预案体系、构建监测预警网络、提升模拟推演应用、强化联合响应能力、夯实精准救援能力）。

逐段对照本项目：

| 论文段 | 本项目承接 | 是否覆盖 |
|---|---|---|
| 预案 | 39 条规则逐条 `source_ref` 到预案行号 | ✅ 覆盖 |
| 监测 | `weather_alerts.csv` + 雨情预警（预报值，非实测传感器） | ⚠️ 部分：无物联感知 |
| 推演 | 六跳 `DEDUCTION_STAGES` + 产流标定 + 过程线 | ✅ 覆盖 |
| 协同 | 协同层 26 卡 / 15 序 / 6 角色 + 冲突 C1–C3 | ✅ 覆盖（但为离线推演，非在线会商） |
| **救援** | **无**。动作清单止于恢复通行、退水判定 | ❌ **不覆盖** |

结论：讲稿与页面只对齐前四段，**不写「救援」**。写成五段会引出「救援力量调度在哪」的追问，而本项目没有队伍级调度（最远只到派工与到场时刻推算 09:50）。

## 6 硬约束：这五篇现在都进不了 `source_ref`

这是本轮最重要的一条，先于摘录卡动笔就要固定。

规则校验的实际链路（`src/decision_poc/deduction.py:332` `verify_rules`）：

```
rules.json 里的source_ref
   → 按 "#" 拆成 (文件名, 定位)
   → 文件名必须能在 load_urban_assets(root) 的资产清单里找到   ← 硬门槛 ①
   → _read_locator 按 line:N / line:N-M / row:N 取原文行        ← 硬门槛 ②
   → rule.keyword 必须出现在该行文本中（子串匹配）               ← 硬门槛 ③
```

三条门槛的后果：

| 门槛 | 后果 |
|---|---|
| ① 文件名须在资产清单 | 资产清单来自 `URBAN_ASSETS`（19 项硬编码规格）。要把文献摘录卡注册成资产，必须改 `URBAN_ASSETS` 并重建 `manifest.json` |
| ② 定位必须是行号 | 论文页码不能直接当定位，摘录卡必须写成「一行一句」的固定排版，行号才稳定 |
| ③ keyword 子串匹配 | PDF 文本层有断行与全角空格，原句必须逐字清洗后才可能通过匹配 |

改 `URBAN_ASSETS` + 重建 manifest 的连锁代价（与既有审计 §8 P2 同级或更高）：

- 资产数 19 → 19+N，`asset_count`、`type_counts`、`modality_counts`、`source_org_counts` 全部变化；
- `manifest.json` 字节变化 → 台账一致性检查与 `expectations_digest` 重算 → 21 个 `.md/.py` 与 3 份 docx/pptx 需一次改完；
- 与「samples 目录按 sha256 记账、一个字节都不能改」的既有纪律直接冲突。

**因此本轮结论：三份摘录卡定位为「内部依据文档」，只支撑写文档、讲稿与页面口径，不注册为资产、不写入任何 `source_ref`、不进 39 条规则。** 要进 `source_ref` 单列为后续阶段，需先评估 manifest 重建的连锁影响，并单独出方案。

### 6.1 若将来真要接入，三条路径的代价对照

项目里已有「台账之外的补充资料」通道 `SUPPLEMENTARY_ASSETS`（`src/decision_poc/urban_dataset.py:317`，现有 2 条：真实定级过程、雨量映射说明）。其注释写明："`URBAN_ASSETS` 那 19 项是演示场景的业务台账……长度是冻结数字……放进同一张表会让『台账条目数』这个数字失去意义"。文献摘录卡属于这条通道描述的那类资料，不属于业务台账。

| 路径 | 能进 `source_ref` | 代价 | 评价 |
|---|---|---|---|
| A 进 `URBAN_ASSETS` | ✅ | 破坏"19 项业务台账"语义（代码注释已明确反对）；`asset_count`/`type_counts`/`modality_counts`/`source_org_counts` 全变；manifest 重建 → `expectations_digest` 重算 → 21 个 md/py + 3 份 docx 一次改完 | 不建议 |
| B 进 `SUPPLEMENTARY_ASSETS` | ❌ | `rel_path` 相对 `samples/`，摘录卡要挪进 `samples/references/`，而 `samples/` 按 sha256 记账；只解决"可登记、可检索"，不解决"规则依据" | 慎用 |
| C 给单条 `DeductionRule` 加不参与校验的 `method_ref` | ❌（但表达力足够） | 1 个可选字段 + 1 条校验；39 条规则原样不动；manifest 不动 | **推荐** |

推荐 C 的理由：文献证明的是"这条规则为什么这么设计"（方法依据），台账证明的是"这条规则的阈值出自哪一行"（事实依据）。两者混在 `source_ref` 里，会让 `source_ref` 的举证力被稀释——读者无法分辨某个 `line:N` 指向的是台账还是论文摘录。分开两个字段，`source_ref` 保持"只指向业务台账"的纯度，`method_ref` 承载方法出处且**不参与** `verify_rules` 的 keyword 匹配。

**字段落点**：`source_ref`、`keyword` 都挂在单条 `DeductionRule` 上（`deduction.py:125`），而每条规则的方法依据各不相同（一条来自 GB 50014、一条来自预案、一条来自本项目重算），不存在规则集级别的方法依据。因此 `method_ref` 应加在 **`DeductionRule`**，不是容器 `RuleSet`。本文件若在别处写了"给 `RuleSet` 加字段"，以本句为准。

若选 B 或 C，前置动作相同：**先把摘录卡改成"一行一句"的固定排版**。当前卡片体（原句嵌在列表项内、带加粗与引号）行号不稳定，任何编辑都会让 `line:N` 漂移；而 `line:N` 定位一旦漂移，校验是直接报错而不是降级。


### 6.2 method_ref 影响审计（2026-11-19，只读核查）

五项逐一查代码后的结论：

| 项 | 代码事实 | 结论 |
|---|---|---|
| 1 类型与序列化 | `RuleSet`、`DeductionRule` 都继承 `StrictModel`（`contracts.py:9`，`extra="forbid"`）；`load_rules()` 用 `model_validate()` | 新字段必须先声明，否则现有 JSON 会因未知字段被拒；声明后 `model_dump()` 自动包含 |
| 2 快照与摘要 | `expectations_digest()` 只取 `schema_version` 与 `checks`（`evidence_check.py:401`）；推演快照来自语义库；`RuleRef` 只存 `rule_id`/`source_ref`/`version`（`provenance.py:69`） | 不改变摘要、快照哈希或规则版本值 |
| 3 其他校验器 | `verify_rules()` 只读 `source_ref`/`keyword`/`rule_id`；引擎读 `when`/`then`/`priority`/`confidence` 等显式字段；无遍历全部字段的校验器 | 字段会被加载但不参与校验与推演 |
| 4 测试字段约束 | `test_deduction.py:299/313` 的两个 `stripped` 测试是"剥规则"不是"剥字段"；全仓无 `model_fields`/`__fields__`/字段数断言 | 不触发字段白名单 |
| 5 数字守卫 | `rules` family 统计 `len(load_rules().rules)`（`test_frozen_numbers.py:203`） | 无"规则字段数"守卫，基线不动 |

补充三条核查结果：

1. **全仓无 `rule.model_dump` / `rules.model_dump` 调用**（只有测试里构造 `RuleSet`）。所以"dump 会多一个键"当前没有落盘后果；但将来若有规则集导出，`model_dump()` 默认包含默认值，会新增 `"method_ref": ""` 键，需用 `exclude_defaults` 或显式白名单，不能默认它是透明的。
2. **兼容性是单向的**：新代码读旧 JSON 可以（可选字段有默认值），旧代码读新 JSON 会因 `extra="forbid"` 直接报错。字段上线后，旧版本不得再读新规则文件。
3. **已有同构先例**：`assumption: bool = False` 与 `assumption_note: str = ""` 就是可选字段 + 默认值，`method_ref` 照此写法即可，不需要新机制。

审计结论：不存在重复字段，不触发冻结数字，不动 manifest。实现阶段的前置条件已满足（是否做由后续决定）。
