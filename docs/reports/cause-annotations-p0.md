# 成因标注表 P0（A-03 / B-01）

日期：2026-11-18　　状态：**只读标注，未进代码、未改规则文件、未改台账**

用途：把「四类成因」落成可核对的标注，先固定每条的证据等级与可陈述边界，供后续 P1（大屏挂 `cause_tags`）与 P3（情景固化）直接引用。

---

## 0 使用前提（先读这四条）

1. **场景前缀**：本表默认数据集为 `samples/assets/urban/`（六跳、缺口、自检都用这一份）。`samples/scenarios/real_20260801/` 是真实暴雨变体，与默认数据集**只差 `weather_alerts.csv` 一张表**（其余台账逐字节相同），因此只有「降雨」一行的标注随场景变化，其余各行两份通用。
2. **键名固定**：`rain` / `expansion` / `drainage` / `management`，与四类成因一一对应，便于后续序列化。
3. **等级定义**：`real`=台账或文件可定位到具体行；`derived`=由实测量按公式/规则算出；`assumption`=无出处、演示假设（必须显式标注）；`missing`=无数据，只能声明缺什么。
4. **一句一证据**：每行只承载一句可陈述的话；写不进「依据」的，就不许写成结论。

## 2 B-01（事件 WO-20261029-011，滨河路 R-201，09:30 报 18cm）

### 2.1 逐项判级

| 子项 | 等级 | 依据 | 结论 |
|---|---|---|---|
| 降雨 | real | `weather_alerts.csv#WA-20261029-02`（yellow，30 mm/3h，B-01） | 黄警 30 mm/3h，雨量小于 A-03 |
| 低洼地形 | **不成立** | `road_network.csv#R-201`（`elevation_m=5.4`） | 5.4 m 高于 R-101 的 3.2 m，**不是片区最低点**，不能套「低洼」成因 |
| 施工影响 | **不适用** | `construction_plans.csv#CP-2026-052`（`start_at=2026-10-30T08:00`） | 事件时点 10-29 09:30，施工尚未开始，排除 |
| 泵站 | real（正常） | `drainage_facilities.csv#DF-PS-03`（1800 m³/h，`failed_units=0`，`backup_power=yes`，state `in_service`） | 运行正常，不构成成因 |
| 雨水口 | real（正常） | `drainage_facilities.csv#DF-IN-201`（`in_service`，`last_inspection=2026-09-18`） | 未淤积，不构成成因 |
| 管网 | real（达标） | `pipeline_ledger.csv#PL-DRN-201`（DN800，2018 年，note「重现期达标」） | 能力达标，不构成成因 |
| 河道顶托 | **missing** | 无外部水位边界 | 不参与计算 |
| 管理缺位 | real（无缺口） | 需求 2 台 / 库存 2 台（`RES-PUMP-M-B01`）；`owner_org=ORG-DRAIN` 明确 | 无资源缺口、无责任空白 |

### 2.2 归因结论：**无设施型成因，标注为「无法归因」**

四类成因在 B-01 上没有一条能由台账支撑：雨量更小、地形更高、泵站正常、雨水口在服务、管网达标、资源无缺口。18 cm 的积水**落在成因分类法之外**。

与之相关的是模型口径问题，不是城市机理问题：

- `service_band.csv#R-201`：状态 `pending`，默认服务带 54 m，按台账 18 cm 反推需 67 m，**差 31%**；
- 也就是说，B-01 的 18 cm 与「服务带宽度取统一默认值」有关，属标定口径待核实项。

因此 B-01 的正确输出是：

```
成因标注：无设施型成因可归（四类均不成立）
已知偏差：服务带宽度按 54m 默认值取，台账 18cm 反推需 67m，差 31%，待现场核实
不参与计算：河道顶托
```

**禁止**：把 B-01 标成「城市扩张·低洼」或「排水能力不足」来凑满四类。B-01 是这套分类法的**反例样本**——它证明分类法不是万能的，这一点比给它硬安一个成因更有价值。

## 4 句式与挂接位点（供 P1 直接照做）

**唯一允许的句式**：

```
<成因名> —— <关键台账值>（<file>#<主键>）；等级 <real|derived>
```

因果句式（「因 A 导致 B」）只在一种情况下可用：由 `rerun_with_interventions` 重算得出，且两侧数字都在。凡没有重算对照的，只能写并列。

**挂接位点**（P1 执行时用，本次未改）：

```json
cause_tags: [
  {"key": "drainage.pump_fault", "label": "排水能力不足", "level": "real",
   "evidence_ref": "drainage_facilities.csv#DF-PS-01"},
  {"key": "drainage.intake_clog", "label": "雨水口淤积反涌", "level": "real",
   "evidence_ref": "drainage_facilities.csv#DF-IN-101"}
]
```

- 可挂在 `out/map2d/event_timeline.json` 的 `jumps[i]` 上（复用已有 `basis=ledger|derived` 字段风格）；
- 或挂 `DeductionStep(observed)`（P2，需加可选字段并改验收，代价最大，放最后）。

## 5 与本表相关的既有结论（不要重复推翻）

- 泵站故障是主因构成，写「次生原因：泵站故障」会被本表 §1.3 判为错因；
- 道路、基坑、燃气、供电是**并发**影响，不是「封路导致基坑进水」（基坑沉陷工单 09:35，半幅封路 08:30 已生效）；
- 三情景实测（需求/库存/缺口）：基线 8/6/2、泵站正常 5/6/0、加调 2 台 8/8/0；两种干预都只消掉 C3，**C2 稳定存在**；
- 不使用 MIKE 论文的 MAE/R² 口径：本项目 1 标定点 + 1 验证点，且验证点偏差 −31%。
