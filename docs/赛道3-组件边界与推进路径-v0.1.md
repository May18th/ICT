# 赛道 3 组件边界与推进路径 v0.1

> 定位：本文只回答三件事——**四个外部组件各自扮演什么角色、能借到哪一步、哪一步不能碰**；
> **先做什么后做什么、依赖谁、怎么判定做完**；**哪里会翻车**。
> 方案的业务主线仍以 [ICT-创新赛-赛题3-方案与实施计划](ICT-创新赛-赛题3-方案与实施计划.md) 为准，
> 接入细节以 [Nexent 集成边界](nexent-integration-boundary.md)、[北向传输层设计](nexent-northbound-transport-design.md) 为准，本文不重复。

## 0 一句话立场

**Nexent 是编排与会话的运行时，不是策略计算引擎；IUDSim 是反馈信号的生产者，不是被集成的子系统；
h2oai 只贡献角色分工的形状；审计框架只贡献"锚定关键反馈"这一个动作——而这一步我们自己的 `anchoring.py` 已经做完了。**

由此推出一条硬边界：

> 凡是**要写进说明数字**的东西（12 例复现、训练/留出偏差、采纳与拒绝轮次、回滚逐位复原），
> 必须走本地确定性路径（`allocation.py` → `policy_evolution.py` → 校验 → 版本注册表）。
> Nexent 负责**把反馈编排成候选、把理由讲清楚、把工具串起来**，不负责算出那个数。
> 让 LLM 参与数值校验，等于主动放弃 12/12 可复现与 108 项自检。

## 1 四个组件的定位与借鉴边界

| 组件 | 在方案里的真实位置 | 可复用（直接用） | 仅作参考（抄设计不抄代码） | 不可直接套用 / 集成 | 我们与它的接触面 |
|---|---|---|---|---|---|
| **Nexent v2.7.0**（ModelEngine-Group/nexent，本地已在 `D:\华为ICT\Nexent`） | 运行时底座：会话、Agent 生成、工具注册、过程观测 | Docker 部署形态；北向 `/nb/v1/chat/run` SSE 契约（本地 `nexent_transport.py` 已实现）；MCP 工具注册；`verification.py` 的"校验→带修复指令重试"回路；`observer.py` 的过程事件流 | Agent 分工的提示词组织方式；记忆版本化（`memory/dreaming/version_builder.py`） | ① 不能用它的自校验回路替代策略校验；② 不能把编排循环塞进 LangGraph 之外（会分裂成两套状态机）；③ `context/handlers/*` 10 个 handler 目前是孤儿模块（审计已确认未被引用），别指望开箱即用 | 北向 API + MCP 工具注册；**不改 Nexent 源码** |
| **IUDSim**（THU-iUWLab/iudsim） | 物理沙盘：生产"泵站开了之后水位怎么变"这类反馈信号 | 不集成代码。只取**输入/输出语义**（降雨、管网、地表径流、顶托、社会响应 → 水位/淹没/绕行） | "紧耦合地表-管网-河流"的过程划分，用来校验我们的反馈字段有没有漏项 | ① 研究型模拟器，许可与依赖未在本机核实，**不能写进交付物依赖清单**；② 不能作为演示时的实时组件（跑一次可能几分钟，撑不住 30 秒响应） | 一个 **adapter 契约** `FloodFeedback`，后面接谁都能换 |
| **h2oai-flood-intelligence-agent**（Apache 2.0） | 协同工作流蓝图：跨部门角色怎么切、谁看什么数据 | 无（技术栈 H2O/NVIDIA，与本项目不兼容） | ① 角色切分（采集/研判/推演/协同）；② "ML 模型随新灾情迭代"→ 我们的"最差维度归因→候选参数"；③ 每个角色只看自己白名单工具 | 代码、模型、pipeline 一律不引入；不要为了"对齐蓝图"新增 5 个 Agent 角色 | 设计参照。**我们已有 `ROLE_TOOL_GROUPS`（drain/road/traffic/gas/power 五个角色白名单），分工形状已经落地**，不需要照抄 |
| **Agent 审计框架**（agentaudit-core / nwu-protocol / OpenBrain） | 可信溯源思路：把"触发策略调整的那条反馈"锚定成可复核承诺 | 不引入依赖 | Merkle Proof / 哈希链 / 原文链下、承诺上链 的分层 | ① 不能真接区块链（无节点、无共识，说明一问就穿）；② 不能宣称"不可篡改存储" | **已自建 `anchoring.py`**：承诺元组 `(H(o), H(Z), H(a*), meta)` + 链下原文 + `verify_offchain()`，比引入外部框架更轻、更可控 |

### 1.1 三条容易越界的表述

1. **"零代码生成智能体"≠ 我们的方案不需要写代码**。零代码是 Nexent 的建 Agent 方式，我们的价值在工具、校验、数据和流程，别把平台能力讲成自己的创新。
2. **"6,100+ Stars"不进方案**。星数不是技术论证，评委不看这个。
3. **IUDSim 只写"物理沙盘（参考）"**，不要写成"已集成清华模拟器"。真跑通之前，这条只能出现在"后续工作"。

**P0.1 登录报"认证服务当前不可用"——两个真因（2026-11-11 15:00 修完）**

表面看是 supabase 认证故障，实际是**后端根本没起来**。web 的 `HTTP_BACKEND=http://nexent-config:5010`，
config 死了前端就统称"认证服务不可用"。

1. **OTEL 协议非法**：`deploy/env/monitoring.env` 原值 `OTEL_EXPORTER_OTLP_PROTOCOL="http"`，
   而 FastAPI 自动埋点只接受 `http/protobuf`，于是 `config` 与 `runtime` 启动即
   `Application startup failed. Exiting.`。改为 `http/protobuf` 后**必须 `--force-recreate`**——
   env 在容器创建时固化，`docker restart` 读不到新值。修复后 runtime 日志出现
   `Uvicorn running on http://0.0.0.0:5014`、config 出现 `5010`。
2. **`.env` 里的管理员口令与库内不一致**：`suadmin@nexent.com` 是早先部署建的，`deploy.sh` 见其存在就跳过创建，
   所以 `NEXENT_SUPER_ADMIN_PASSWORD` 后来改过也对不上。修法（库名是 `supabase`，不是 `postgres`；
   pgcrypto 在 `extensions` schema）：
   `update auth.users set encrypted_password = extensions.crypt('<pw>', extensions.gen_salt('bf')) where email='suadmin@nexent.com';`
   改后 `POST :3000/api/user/signin` → **200 / role=SU**。
   库里另有一个 `admin@nexent.com`（ICT 镜像自带，口令未知），别用。

**附带教训（会再踩）**：`docker compose up -d --force-recreate <svc>` **会连带重建它的依赖**。
本次重建 runtime 时把 ES 一起 recreate，而 `--env-file ../.env.generated` 里没有 `ELASTIC_PASSWORD`
（原部署靠 `source deploy/env/.env` 的 shell export 传值），ES 空密码 → unhealthy → runtime 起不来。
正确姿势：先 `set -a && source deploy/env/.env && set +a` 再跑 compose，或直接重跑 `bash deploy.sh --defaults docker`。

**P0 遗留的两件事（P1 的前置）**

1. **没有配模型**：`deploy/env/.env` 里只有空模板变量。**注意：Nexent 不读宿主机的 `DEEPSEEK_API_KEY`**，
   它把模型存成租户级记录（`model_record_t`），必须在 UI 里显式登记，否则 `chat/run` 直接报无可用模型。
   内置目录 `backend/configs/model_catalog.json` 已有 `deepseek` 供应商，预置字段：
   `base_url=https://api.deepseek.com/v1/`，`llm` 类型下挂 `deepseek-v4-pro`（旗舰）/ `deepseek-v4-flash`（低成本）。
   路径：`/zh/models` → 添加模型 → 选「DeepSeek 官方平台」→ 填 key → 选模型 → 保存后**设为默认 LLM**。
   若目录里的模型名与你账号可用的不一致，改用自定义模式，模型名按账号实际可用值填（如 `deepseek-chat`）。
2. **Docker 只分到 7.9 GiB**（`MemTotal=8327397376`，低于推荐 16 GiB）。当前 `nexent-data-process` 常驻约 4.3 GiB，总占用约 6.3/7.75 GiB（≈80%）。**一旦真正跑推理，OOM 概率高**——先调 Docker Desktop 的内存上限到 12 GiB 再压测。

### P1 读懂并验证"反馈循环与控制平面"（只读，不改业务）

这一步不是"跑起来"，是**把宣传词落到具体文件和行为上**，否则说明讲不清"可进化"靠什么。

**落点（源码级，已核对，2026-11-11）**

| 机制 | 代码位置 | 关键事实 |
|---|---|---|
| 自校验（三层） | `sdk/nexent/core/agents/verification.py`、`core_agent.py:2026` | `AgentVerificationConfig` 分 `step_verification`（ReAct 每步）/ `final_verification`（最终答案候选）/ `llm_verification`（确定性检查之后再用 LLM 当裁判）；失败时 `phase="repair"`，`verification_round < max_final_rounds` 才重试 |
| **默认状态** | `core_agent.py:544`、`:1936` | **`AgentVerificationConfig(enabled=False)`——默认关闭**；关闭时 `max_final_rounds=1`，即"不修"。**开箱建一个 Agent 是看不到任何校验事件的** |
| 护栏（正则规则引擎） | `agent_model.py:160-208`、`core_agent.py:690-735` | `GuardrailRule(name, pattern, severity)` 正则匹配，逐条短路；命中即拦工具入参或直接澄清退出；规则可由 LLM 生成（前端 `GuardrailConfigContent.tsx` 有 ai.generate / ai.candidate / ai.import） |
| 事件出口 | `verification.py:813-825` | `emit()` → `observer.add_message(..., ProcessType.VERIFICATION, payload)`，payload 含 `phase / event / round / severity / score / failed_criteria / repair_instruction / passed` → 走 SSE 到前端 |
| 上下文策略 | `core/agents/context/handlers/*` | 10 个 handler 仍无引用点（孤儿），不要当作可用能力对外讲 |

**这张表就是 P1 的交付物**：它把"内置反馈循环和控制平面"从宣传词变成了可指认的 5 个位置，并明确
**默认关闭、需要显式开启**这一事实。

**实测（2026-11-11 15:05–15:25，北向 SSE 抓包，证据见 `artifacts/p1-nexent/`）**

用同一句必然触发规则的提问（含 11 位手机号）在 `urban_llm_decision_agent` 上跑四组：

| 组 | 配置位置 | 耗时 / 事件行数 | `verification` 事件 |
|---|---|---|---|
| A 基线 | `verification_config = null` | 19.8 s / 516 | **0 条** |
| B 只改草稿 | v0 开启 | 9.4 s / 426 | **0 条**（对话读的是已发布版本 v2，v2 仍是 null） |
| C block | v2 开启，规则 `\d{11}` → block | 2.7 s / 7 | 1 条，`phase=blocked`，**模型一次未调用** |
| D mask | v2 开启，规则 → mask | 43.3 s / 4521 | **39 条**，覆盖 8 个步骤 |

组 D 的相位分布（这就是"反馈循环"的真实形状）：

```
guardrail_input   phase=warning    passed=true   ×8   （手机号被脱敏为 ***，放行）
tool_precheck     phase=pass       passed=true   ×8
guardrail_output  phase=pass       passed=true   ×8
code_execution    phase=pass       passed=true   ×6
final_answer      phase=start/pass passed=true   ×6
final_fail        phase=final_fail passed=false  ×1   round=1, score=0.25,
                                                       failed_criteria=[intent_coverage, evidence_grounding]
repair            phase=repair     passed=false  ×1   带 repair_instruction
final_pass        phase=final_pass passed=true   ×1
```

**结论**：回路确实是 **`final_fail` → `repair`（带修复指令）→ `final_pass`，上限 `max_final_rounds`（默认 2）**，
全程在一次会话内完成，不改任何版本号。**这正是"轮内修复"，与"跨版本进化"是两回事。**

**三个工程坑（都会让人误判成"机制不存在"）**

1. **改草稿不生效**：`POST /agent/update` 只写 `version_no=0`（草稿）；对话读的是已发布版本。
   本次三个版本的 `verification_config` 原本都写的是 JSON `null`，改完草稿后对话仍无任何事件。
2. **`verification_config: null` 清不掉**：更新实现里 `if value is None: continue`，传 null 等于没传，只能改库。
3. **`version_no` 不能放进请求体**：它会被当成字段写进 `UPDATE ... SET version_no=...`，撞 `ag_tenant_agent_t_pkey` → 500。

**验收（已达成）**
1. 抓到 `guardrail_input` 与 `final_fail→repair→final_pass` 两类事件，字段与代码一致；
2. 组 A 与组 D 构成 A/B 对照，**同一提问、同一 Agent，仅差配置**，"默认关闭"有反向证据；
3. 实验后已把 `agent_id=37` 三个版本的 `verification_config` 全部还原为 NULL（`UPDATE 3`），未留改动。

**风险（最高的一条）**：把 Nexent 的"LLM 自校验-重试"讲成"策略进化"。两者机制完全不同——
前者是**同一轮内的输出修复**（phase: pass → repair → final_pass，轮次上限在配置里），
后者是**跨版本的参数变更 + 校验 + 回滚**。讲混了会被一问击穿。

### P2 IUDSim 出内涝数据（契约先行，允许降级）

**做法**：先写 `FloodFeedback` 契约与 adapter 壳，用现有 `samples/scenarios/vd02` + 现有推演的时序结果填 fixture；
IUDSim 真跑通后再替换实现，**上层零改动**。

**契约字段（建议）**：`scenario_id / t_min / district / water_depth_cm / flooded_road_ids / pump_state / source(real|sim|fixture) / seed`。
`source` 字段是合规红线——真/合成必须能分辨，不能含糊。

**验收**
- 同一 `scenario_id + seed` 跑两次，字段级一致（浮点给容差）；
- 至少 3 个时点 × 全片区覆盖；
- `source=sim` 的记录能指出 IUDSim 的版本与参数文件。

**风险**：IUDSim 环境（依赖、许可、编译）可能吃掉一整周。**设 2 天止损线**：跑不通就永久降级为 fixture，并在文档里如实写"参考未集成"。

### P3 最小流程（核心验收，其余都是它的附属）

> **唯一性约定（全节有效，先立规矩）**
> 全系统**唯一生产策略是 `flood-response-v1.2`**，代码里的单点是
> `policy_evolution.PRODUCTION_LABEL`。凡"当前用哪一版"的问题只认它一个答案；
> 后面提到的 `v1.3` 是口径敏感性实验的副产品，**不提升为生产、不进运行期记忆、不进平台台账**。
> 现有事实：运行期记忆只有 1 条 v1.2、反馈流水全部 v1.2、平台台账只有 v1.2。

链路：`数据输入 → Nexent 决策（调 allocation_plan 等 MCP 工具）→ 手动注入反馈 → 策略调整 → 回读版本`

**这条链路的前半段已经存在（2026-11-11 核实，P3 工作量小于原估）**

- 容器 `urban-twin-mcp:dev` 跑的就是本项目自己的 MCP：`python -m decision_poc.mcp_sse --port 8000`（宿主 18000）；
- Nexent 工具表 `nexent.ag_tool_info_t` 共 48 个工具，其中 **15 个 `source=mcp`**：
  `allocation_plan / claim_trace / collab_run / conflict_check / doc_search / event_deduce / asset_lookup / counterfactual_run` 等；
- Nexent 里已有 4 个 urban 系 Agent（`urban_llm_decision_agent` / `urban_collab_agent` / `urban_deduction_agent` / `urban_control_no_tools`）。

**所以 P3 不是"从零接入工具"，而是"补上缺的那一段"**：反馈注入 → 校验 → 版本回读。
真正要新写的只有 ①`FloodFeedback` 契约与注入接口、②Nexent 侧把反馈串进来的编排。

**记忆已接通（16:56，warm start）**

起始值仍是 0，原有行为逐位不变）。

与固定记忆里那条（label `flood-response-v1.2`）**完全相同**——entry_id 由
`signature + label + params + outcome` 哈希得出，说明运行时结果与固定资产一致，不是另算了一套。

**评审（第二进化信号）已接入（17:04）**

`run_evolution()` 现在默认读 `samples/eval/decision_reviews.json`（**只读**）并传给 `evolve(reviews=...)`。
只有 `decision=modify` 且给了修正分配的评审才会变成校验用例；`reject` 只留痕、不编期望。

它的作用必须说准：**评审只能否决，不能驱动**。

- 校验要求候选在评审用例上的偏差 = 0（与专家给的修正分配完全一致），偏差 > 0 直接拒掉整轮；
- 而训练偏差为 0 时，评审无法让偏差再下降，所以**不会带来新版本号**。

实测（`REV-001`，专家期望 A-03:5 / B-01:1）：

| 评审 | 结果 |
| --- | --- |
| 按专家判断 5:1 | `v1.2`，2 轮采纳，**评审偏差 0.117143 → 0.0000** |
| 反向构造 4:2（验证用，未入库） | 停在 `v1.0`，**0 采纳 / 1 拒绝**，理由「违反人工评审结论（评审偏差 0.1171）」 |

第一行是很有力的一条：**算法自己收敛出的策略，恰好等于专家手工修正的分配**——v1.0 违反专家判断
（偏差 0.1171），v1.2 与专家完全一致（0.0000）。第二行证明评审有实权：专家期望一变，整轮候选全被拦。

页面流水已加「记忆」「条目」「评审偏差」三列，显示 `v1.0 → 最终` 的专家一致性与记忆命中情况；
未触发演化的行显示 `—`，不伪装成"从 v1.0 起步"。

**结论（修正过一次，以本节为准）**：在**单一口径**（阈值型）下 `v1.2` 是终点——记忆负责"不重复学"、
评审负责"别学歪"，两者都不是新信号的来源，反复提交同一场景的反馈不会让版本号继续走。

但"终点"只对单一口径成立。**引入第二个口径后还能继续演进，而且不破坏原口径**，见下一节实测。
所以准确表述是：**策略是口径的函数，扩信号源靠"换口径"，不靠"多提交"**。

**口径敏感性对照：v1.3 是怎么来的（17:26，`scripts/policy_sensitivity.py`）**

先排除一个看似可行但实为循环论证的做法：仓库里那 120 条扩充集
（`dist/qlora/allocation_cases_gen.json`）标签由 `decide()` 在 v3 参数下生成，
而 **v3 与 v1.2 参数完全相同**。拿它当校验等于"用 v1.2 的输出去评测 v1.2"，
实测偏差 **0.000000（四个维度全 0）**，一个字都学不到。这不是数据量不够，是循环论证。

正确做法是**控制变量换标注口径**：场景输入完全不变（120 组与扩充集逐一对应），
只把标注规则从"阈值型"（`weight_depth=0`，只看是否过封路阈值）换成"水深敏感型"
（`weight_depth=0.5`）。同一批场景，两套口径：

| 策略 | 水深敏感口径偏差 | 阈值口径（固定 12 例）偏差 |
| --- | --- | --- |
| v1.0 | 0.0641 | 0.0333 |
| v1.1 | 0.0562 | 0.0314 |
| **v1.2** | **0.0287** | **0.0000** |
| depth-0.5 | 0.0000 | 0.0000 |

**排序反过来了**：v1.2 在阈值口径最优，在水深敏感口径只排第二。这就是"策略贴着一套口径调出来"的证据。

在新口径上跑演化（从 v1.0 起，最多 6 轮）得到一个**真正的帕累托改进**：

```
标签      flood-response-v1.3
参数      weight_closure=1.0, weight_hazard=0.25, weight_depth=0.02, transfer_penalty=0.1
新口径    0.2219 → 0.0244（3 轮采纳 / 1 轮拒绝，优于 v1.2 的 0.0287）
冻结 12 例 0.0000
```

**最关键的一条验证**：逐例比对 v1.2 与 v1.3 在固定 12 例上的 `decide()` 输出
（分配 / 跨区调拨 / 处置顺序），**12 例全部逐字段相同，0 处差异**。
所以 v1.3 不是"用 12 例的分数换新口径"，而是**在 12 例行为完全不变的前提下多覆盖了一套口径**。
注意 `weight_depth=0.02` 是演化自己找到的**最小改动**（不是照抄对照口径的 0.5）——这正是校验"只挑训练偏差最小补丁"的结果。

产物写 `artifacts/policy/sensitivity/`（`depth_sensitive_cases.json` + `summary.json`），已 gitignore，
且**交付前已清理**：需要时跑一次脚本即可重建（实测两次运行产物逐字节一致，sha256 可对）。
保留的是"能复现实验的脚本 + 这份结论"，不保留"另一套策略参数的具体数值"——
数据层面必须只有一个答案。**不改动 `samples/eval/` 任何文件**，固定的 12 例与 108 项自检校验值均未变动。

**v1.3 不提升为生产**，理由三条，写进产物字段 `promotable: false`：

1. 12 例是唯一带依据条款的 ground truth；"水深敏感"口径是**我们自己设的对照**，
   没有业务依据——拿它当训练目标，等于自定目标再自证达标；
2. 若 v1.3 成为默认，"当前策略是哪一版"就有两个答案（台账写 v1.2、参数里却有 `depth=0.02`）；
3. v1.2 的每个参数都能追到 12 例上的具体偏差（R1 `weight_closure/transfer_penalty`、
   R2 `weight_hazard`），而 `weight_depth=0.02` 只能追到"让对照口径好看一点"。

脚本里有可执行护栏 `assert_production_singleton()`：生产标签若不是 `v1.2`、
或该版本参数与固定记忆不一致，脚本直接失败——不靠人记，靠代码拦。


**平台可见：策略台账同步进 Nexent 知识库（17:22，B 线）**

本地流程此前只在 `web_demo` 里看得见，平台上的 Agent 不知道"当前策略是哪一版"。
现在补上了单向镜像：

```

   → deploy/nexent/sync_policy_ledger.py（按版本归并，取首次达成那条）
```

三个设计决定：

1. **单独建索引，不混进 `urban-flood-assets`**。业务资产是泵站/道路/组织职责，策略演进是元数据；
   混在一起后问"泵站设计流量"会命中"v1.2 偏差 0"，检索质量直接垮。
2. **台账取"首次达成该版本"那条，不取最后一条**。同一版本反复提交会命中记忆，那一轮降幅是 0、
   采纳 0 轮；写进台账就变成"这一版什么都没做"，把真实收益（0.2264→0）盖掉。
3. **先按 `path_or_url` 删同键旧文档再写**，否则每次同步都在索引里堆一条同版本记录。

实测：平台 Agent 被问「当前决策策略是什么版本？训练偏差降了多少？」→ 调 `knowledge_base_search`
（自动选 `urban-policy-ledger`）→ 回答

> 当前决策策略版本为 **flood-response-v1.2**（出处：policy-ledger.md）。训练偏差降幅为 **0.226428**。

数字与本地台账逐位一致，且带出处引用。索引 id 无法按名字反查（`GET /api/indices` 只给 id 列表），
所以首次创建后缓存到 `artifacts/policy/ledger_index_id.txt`，缓存失效时探测重建。

**还没做的**：①未把反馈注入做成 MCP 工具——曾试过并**已回滚**：那等于让模型自己注入反馈、
自己触发策略调整，与"反馈必须手动注入"直接冲突。
②`final_label` 已能进平台知识库被 Agent 检索，但**未回写 Agent 自身的版本号**——
Nexent 的 `version_no` 是 Agent 配置版本，与策略版本不是一回事，硬塞会造成语义混淆，暂不做。

**关键约束：反馈必须手动注入。** 由人把 IUDSim 结果填成 `FeedbackRecord` 提交，**不让 LLM 自动解释模拟结果**。
理由：自动解释会引入不可复现的语义漂移，12 例口径立刻失效。手动注入不是偷懒，是把变量控制住。
