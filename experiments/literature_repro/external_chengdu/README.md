# 成都本地数据：已终止（2026-11-22）

这条线走到底了，结论是**拿不到可用的时序观测**。保留目录是为了记住判断依据，避免以后有人重复跑一遍。

## 走到的位置

| 步骤 | 结果 |
|---|---|
| 平台定位 | 成都市公共数据开放平台 `https://www.chengdu.gov.cn/data/oportal/`（省级 `scdata.net.cn` 只是入口，账号不通用） |
| 授权 | 已申请到 Client ID / Client Secret，令牌生效（错误的 Client ID 会报「标识不存在」，说明身份校验通过） |
| 接口调用 | 服务端返回 `300 权限认证失败`；6 种签名变体（标准、URL 编码、URL-safe Base64、秒级时间戳、短横线分隔、换行分隔）全部同一错误，判断为接口未授权而非签名错误 |
| 浏览器内调用 | 用户在平台「在线接口调用」页可直接看到数据，说明接口本身活着，只是需要逐条申请授权 |

## 为什么停：数据形态不匹配

平台「道路积水数据接口」（崇州市水务局）返回的是**静态易涝点台账**，不是监测时序：

```json
{
  "CZDMC": "江源中路489号唐人街",
  "JCSW":  "小于0.6m",
  "SBSJ":  "小于2小时",
  "BZ":    "雨季暴雨时才可能发生。",
  "JWDN":  "30°37",
  "JWDE":  "103°18"
}
```

三个关键字段全是文字描述：

- `JCSW` 名义是「监测水位（积水深度）」，实际是三档定性分级（`<0.3m` / `<0.4m` / `<0.6m`）
- `SBSJ` 名义是「上报时间（积水时间）」，实际是持续时长分级（`小于2小时`）
- `BZ` 是一句现象说明

没有时间戳、没有实测数值、没有与降雨的对应关系。所以原本设想的「雨量→水位」时序回归、
四档评估（自拟合 / 随机点留出 / 跨路留出 / 时间外推）**在这个接口上完全不适用**，
不是脚本参数问题，是数据形态本身不匹配。

另有三处质量问题：坐标只有度分（约 1—2 km）、有一条经度明显异常（`103°18`，其余在 `103°39`—`103°41`，
崇州实际在 103°40 附近）、`total` 返回 0 与 data 非空矛盾（总量字段不可信）。

## 为什么不用它做「口径旁证」

台账的三档深度（`<0.3m` / `<0.4m` / `<0.6m`）看起来能给我们用的 30 cm 做个本地背书，
但手上只有 6 条样例、拿不到全量、`total` 字段还是坏的。用 6 条样例去论证「成都官方分级在 0.3—0.6 m」
属于**挑对自己有利的片段**，与项目一贯的口径纪律相悖。所以这条也不写进报告。

宁可说「没有」，不要造一条经不起追问的弱证据。

## 保留了什么

`fetch_chengdu.py` 留着。签名逻辑（HMAC-SHA256 + 毫秒时间戳 + nonce）是可用的，
将来若平台开放真正的时序数据、或换成有离线下载的数据集，这部分不用重写：

```powershell
$env:CD_DATA_CLIENT_ID = "<令牌标识>"
$env:CD_DATA_SECRET = "<签名认证令牌密钥>"
.venv-exp/Scripts/python.exe experiments/literature_repro/external_chengdu/fetch_chengdu.py --dataset probe
```

`--dataset probe` 会先把数据形态判一遍：拿不到数据行、积水深度解析不出数值、
时间范围早于 2023，三种情况都返回退出码 1 并说明原因——正是这次踩到的坑。
